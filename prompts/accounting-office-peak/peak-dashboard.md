# Prompt สร้าง skill `peak-dashboard`

prompt นี้ใช้สร้าง skill ดึงข้อมูลจาก PEAK มาทำ Dashboard เป็น Excel
ตัวจริงอยู่ที่ [`plugins/accounting-office-peak/skills/peak-dashboard/`](../../plugins/accounting-office-peak/skills/peak-dashboard/)

งานเหมือน [`flowaccount-dashboard`](../accounting-office-flowaccount/flowaccount-dashboard.md)
แต่ต่างกันใน 3 จุด และนั่นคือบทเรียนของ prompt ตัวนี้:
**จะเขียน skill ให้ทำงานกับระบบที่เรายังไม่รู้ว่ามีอะไรให้ใช้ ได้อย่างไร**

| จุดต่าง | FlowAccount | PEAK |
|---|---|---|
| ชื่อ tool | เขียนใน reference ได้ (ยืนยันแล้วว่าเป็น tool อ่าน) | **ห้ามเขียนชื่อเลย** — เขียนเป็น "งานที่ต้องหา tool ให้ได้" |
| ด่านตรวจ | tool ที่ไม่รู้จัก → **ถาม** | tool ที่ไม่รู้จัก → **deny** แม้เป็น tool อ่าน (learn-mode) |
| ผลลัพธ์ | จำนวนชีตคงที่ | **จำนวนชีตไม่คงที่** ขึ้นกับ tool ที่มีจริงและที่ผู้ใช้ยืนยันไว้ |

จุดที่สามคือสิ่งที่ prompt ตัวนี้ต้องจัดการให้ได้: skill ที่ผลลัพธ์ไม่คงที่
ต้อง **บอกให้ชัดทุกครั้งว่าครั้งนี้ได้อะไรมาและขาดอะไรเพราะอะไร**
ไม่ใช่ส่งไฟล์ที่ขาดไปเฉย ๆ

# ความรู้โดเมนที่ต้องเขียนลงใน skill

## ก. สี่หลักการที่ทำให้รายงานนี้เชื่อถือได้ — ต้องปรากฏเป็นกฎ ไม่ใช่คำแนะนำ

1. **`ดึงไม่ได้` ไม่ใช่ `0`** — ศูนย์ปลอมหนึ่งช่องทำให้ทั้งไฟล์เชื่อไม่ได้
2. **ทุกตัวเลขมีที่มา** — ชื่อ tool ที่เรียกจริง, พารามิเตอร์, เวลาที่ดึง ของทุกบล็อกและทุก KPI
   แล้วออกเป็นชีตของตัวเอง
3. **ตรวจยอดข้ามแหล่งแล้วไม่กลบ** — ไม่ตรงคือข้อมูล **ห้ามปรับตัวเลขให้ตรงกัน**
4. **ห้ามคำนวณตัวเลขที่ ERP รายงานมาแล้วใหม่เอง** — คำนวณต่อได้แต่ต้องกำกับไว้

## ข. Step 0 — สำรวจ tool แล้วจับคู่งานเอง (หัวใจของ skill ตัวนี้)

เอกสารต้อง **ไม่มีชื่อ tool ของ PEAK เลย** ให้เขียนเป็นตาราง **งานที่ต้องหา tool ให้ได้** แทน:

| งาน | ต้องมี tool ที่ทำอะไร | ถ้าไม่มี |
|---|---|---|
| ยืนยันกิจการปลายทาง | อ่านข้อมูลกิจการที่เชื่อมต่ออยู่ | **หยุดทั้งงาน** |
| งบกำไรขาดทุน | ดึงงบกำไรขาดทุนตามช่วงเวลา | บล็อกนั้น `unavailable` |
| งบแสดงฐานะการเงิน | ดึงงบ ณ วันที่ | บล็อกนั้น `unavailable` |
| งบทดลอง / ผังบัญชี | ดึงงบทดลองหรือยอดตามผังบัญชี | บล็อกนั้น `unavailable` |
| อายุลูกหนี้ / เจ้าหนี้ | รายงานอายุหนี้ หรือ list รายการค้างที่มีวันครบกำหนด | บล็อกนั้น `unavailable` |
| ยอดขาย | list เอกสารขายตามช่วงเวลา | บล็อกนั้น `unavailable` |
| ค่าใช้จ่าย | list เอกสารค่าใช้จ่ายตามช่วงเวลา | บล็อกนั้น `unavailable` |
| เงินรับ-จ่าย | list การรับ/จ่ายชำระ หรือสมุดรายวันรับ-จ่าย | บล็อกนั้น `unavailable` |
| คู่ค้า/ลูกค้า | ค้น contact เพื่อแปลรหัสเป็นชื่อ | ใช้รหัสแทนชื่อ แล้วระบุไว้ |

กฎที่ต้องเขียนกำกับ:
- **ห้ามเดาชื่อ tool** และ tool ที่ไม่แน่ใจว่าอ่านอย่างเดียว **ห้ามลองยิงดู** — ถามผู้ใช้ก่อน
- รายชื่อ tool ที่เคยเจอจริงถูกบันทึกไว้ที่ `${CLAUDE_PLUGIN_DATA}/observed-tools.json`
  โดย hook ของ plugin — ใช้เป็นจุดเริ่มต้นได้
- **สรุปผลสำรวจให้ผู้ใช้เห็นเป็นตาราง งาน → tool ที่จะใช้ → ได้/ไม่ได้ ก่อนเริ่มดึง**
  แล้วถามว่าจะเดินหน้าด้วยชุดที่ทำได้ หรือรอเติม `peak-tools.json` ก่อน
  (Dashboard ที่ขาดครึ่งหนึ่งอาจไม่คุ้มที่จะส่ง — ให้ผู้ใช้ตัดสิน)

## ค. หัวข้อ "เมื่อ tool อ่านถูก deny" — ต้องเป็นหัวข้อของตัวเอง

ด่านตรวจของ plugin นี้ทำงานแบบ learn-mode: **deny tool ที่ verb ยังไม่ได้จัดประเภท
แม้จะเป็น tool อ่าน** (ต่างจาก FlowAccount ที่แค่ถาม) ข้อความ deny จะบอกชื่อ
`<namespace>__<action>` มาให้ ทางแก้ที่ต้องเขียนไว้:

1. ตรวจเองว่า tool นั้นอ่านอย่างเดียวจริง — ไม่ใช่อนุมัติ ยกเลิก ลบ จ่ายชำระ ส่งอีเมล
   แชร์ อัปโหลด หรือปิดงวด
2. บอกผู้ใช้ให้เติมชื่อลงใน `read_tools` ของ `hooks/peak-tools.json`
   และเติมชุดเดียวกันใน `tools:` ของ agent ที่ใช้ค้นข้อมูลของ PEAK
3. ทำบล็อกนั้นเป็น `unavailable` พร้อมเหตุผลว่าถูก deny และรออะไร

และต้องมี **ตารางแยกสามอย่างที่คนสับสนบ่อย** เพราะแก้ต่างวิธีกันหมด:

| สิ่งที่เกิด | ความหมาย | ทางแก้ |
|---|---|---|
| ถูก deny | ด่านตรวจยังไม่รู้จัก tool | ผู้ใช้เติม `peak-tools.json` |
| ไม่มีสิทธิ์ | บัญชีที่เชื่อมต่อไม่มีสิทธิ์อ่านรายงานนั้น | ผู้ใช้แก้สิทธิ์ใน ERP |
| ไม่มีข้อมูล | เรียกได้ แต่ระบบคืนค่าว่าง | ข้อมูลยังไม่ได้ลงในระบบ |

**ห้ามแก้ `peak-tools.json` ให้เองเด็ดขาด** — การขยายสิทธิ์ของตัวเองเป็นการตัดสินใจของผู้ใช้
และมันคือไฟล์เดียวที่กันการเขียนข้อมูลผิดพลาดเข้าระบบลูกค้าในตอนนี้

ข้อเดียวกันใช้กับ agent ค้นข้อมูลของ PEAK: ถ้ามันตอบว่า **"ยังตั้งค่าไม่เสร็จ"
นั่นไม่ใช่ "ไม่พบข้อมูล"** — สองอย่างนี้สับสนกันแล้วรายงานจะมีช่องว่างที่ไม่มีใครรู้ว่าทำไม

## ง. Step 1 — ยืนยันกิจการปลายทาง และเหตุผลว่าทำไมข้อนี้เข้มกว่าที่อื่น

อ่าน `client-profile.md` → ยืนยันว่า ERP ตรง → อ่านข้อมูลกิจการที่เชื่อมต่ออยู่
→ แสดงเทียบเป็นบล็อกชัด ๆ (ชื่อ + เลขผู้เสียภาษีสองฝั่ง + ผลเทียบ) → **ไม่ตรงคือหยุดทันที**

เหตุผลที่ต้องเขียนไว้: **PEAK ให้ผู้ใช้หนึ่งคนเข้าถึงหลายกิจการได้**
สำนักงานที่ดูแลลูกค้าหลายรายจึงเสี่ยงสูงที่จะดึงข้อมูลผิดกิจการ
และ Dashboard ของกิจการผิดรายอ่านดูสมเหตุสมผลทุกบรรทัดจนกว่าจะมีคนเอาไปใช้ตัดสินใจ
ถ้า tool ใดรับพารามิเตอร์ระบุกิจการ ให้ส่งไปให้ชัด **ไม่พึ่งกิจการที่ระบบเลือกไว้เป็นค่าเริ่มต้น**

## จ. Step 3–6

- **Step 3 ดึงข้อมูลลง data pack** — หนึ่งบล็อกหนึ่งการเรียก เขียนลงไฟล์ทันที
  ไม่กองผลดิบไว้ใน context · ผลลัพธ์ยาวให้สรุป/จัดอันดับก่อนเก็บ ·
  ดึงไม่ครบทุกหน้า → `partial` พร้อมจำนวนหน้า
- **Step 4 ใส่รายการตรวจยอด** 3 ข้อตามค่าตั้ง — ฝั่งที่ดึงไม่ได้ส่ง `null` ไม่ใช่ 0
- **Step 5 รันสคริปต์** — ห้ามเขียนโค้ด openpyxl ขึ้นมาใหม่เอง
- **Step 6 สรุปในแชต** — ยกจาก output ของสคริปต์มาด้วย: บล็อกที่ดึงไม่ได้ (พร้อมสาเหตุ 4 แบบ) ·
  กราฟที่ไม่ได้วาง · การตรวจยอดที่ไม่ผ่าน
  และถ้ามีบล็อกที่ถูก deny **ให้ปิดท้ายด้วยรายชื่อ tool ที่ต้องเติมเพื่อให้รันครั้งหน้าได้ครบ**

## ฉ. การแปลงงวด

# สัญญาของ data pack — ส่วนที่สำคัญที่สุดของงานนี้

`references/dashboard-layout.md` คือข้อตกลงระหว่าง skill (คนดึงข้อมูล) กับสคริปต์ (คนวาดไฟล์)
สคริปต์ต้อง **ไม่รู้จัก ERP เลย** — นั่นคือเหตุผลที่สคริปต์ตัวเดียวใช้ได้ทั้ง PEAK และ FlowAccount

```
{
  "meta":   { erp, client, company_in_erp, period_label, compare_label, fetched_at, notes[] },
  "kpis":   [ { name, value, compare, higher_is_better, status, reason, source } ],
  "checks": [ { name, left, right, tolerance } ],
  "blocks": [ { id, sheet, title, status, reason, total_row, source,
                columns: [ { key, label, type, total, width } ], rows: [ {…} ] } ],
  "charts": [ { type, block, cat, values[], title, anchor } ]
}
```

สิ่งที่ต้องกำหนดให้ชัด:
- `status` มี 3 ค่า: `ok` / `partial` / `unavailable` และ `reason` **บังคับ** เมื่อไม่ใช่ `ok`
  — สำหรับ PEAK `reason` ต้องบอกด้วยว่าเป็นกรณีไหนใน 4 สาเหตุ
- `columns[].type` มี 4 แบบ: `text` / `money` / `int` / `pct` (`pct` ส่งเป็นทศนิยม)
- `higher_is_better: false` สำหรับตัวเลขที่เพิ่มขึ้นแล้วแย่ (ค่าใช้จ่าย ลูกหนี้คงค้าง)
- ฝั่งใดของ `checks` ดึงไม่ได้ → `null` แล้วผลต้องเป็น `ตรวจไม่ได้` **ไม่ใช่ `ผ่าน`**
- `charts` อ้าง `id` ของบล็อกและ `key` ของคอลัมน์ ไม่ใช่ค่าที่ก็อปมาแปะ
- **สิ่งที่สคริปต์ทำให้เอง ไม่ต้องส่งมาใน JSON**: หัวไฟล์ (ชื่อ plugin + เวอร์ชันจาก `plugin.json`),
  % เปลี่ยนแปลงของ KPI, แถวรวมแบบสูตร `SUM()`, สีตามสถานะ, ชีตที่มาของข้อมูล, รูปแบบตัวเลข
- ปิดท้ายด้วย checklist ตรวจไฟล์ก่อนส่งผู้ใช้

# ข้อกำหนดของสคริปต์ build_dashboard.py

- อินเทอร์เฟซ: `python3 build_dashboard.py <data.json> --out <ไฟล์.xlsx> [--plugin-root <dir>]`
- **อ่านชื่อ+เวอร์ชันจาก `.claude-plugin/plugin.json` ของ plugin ที่มันอยู่** — ห้าม hardcode
  (สคริปต์ตัวเดียวกันอยู่ในสอง plugin หัวไฟล์จึงต้องออกมาเป็นชื่อ plugin ที่ถูกต้องเอง
  และหัวไฟล์นี้คือสิ่งที่ hook ตรวจหาในไฟล์ `.xlsx`)
- ไม่มี openpyxl → พิมพ์วิธีติดตั้งแล้วออก exit code 3 **ไม่ใช่ traceback**
- `status: "unavailable"` → เขียนแถวเดียวว่าดึงไม่ได้พร้อมเหตุผล พื้นเทา แล้วไม่วาดกราฟของบล็อกนั้น
- ช่องตัวเลขที่ไม่มีค่าใน `rows` → `ดึงไม่ได้` พื้นเทา **ไม่ใช่ 0 ไม่ใช่ช่องว่าง**
- แถวรวมเป็น **สูตร `SUM()` จริง** · กราฟอ้าง **เซลล์จริงข้ามชีต** ไม่ใช่รูปภาพ
- ชีต **ที่มาของข้อมูล** สร้างจาก `source` ของทุกบล็อกและทุก KPI
- พิมพ์สรุปออก stdout: path, หัวไฟล์, บล็อกที่ดึงไม่ได้/ไม่ครบ, กราฟที่ข้าม,
  การตรวจยอดที่ไม่ผ่าน + ประโยคเตือนว่าห้ามปรับตัวเลขให้ตรงกันเอง
- ไม่ต่อเน็ต ไม่รู้จัก ERP ไม่มี dependency นอก stdlib ยกเว้น openpyxl

# กฎห้าม — ต้องเขียนเป็นหัวข้อของตัวเอง

1. **ห้ามเดาตัวเลข และห้ามใส่ 0 แทนค่าที่ดึงไม่ได้**
2. **ห้ามเขียน แก้ อนุมัติ หรือลบอะไรใน ERP** — skill นี้อ่านอย่างเดียว
3. **ห้ามเดาชื่อ tool** และ tool ที่ไม่แน่ใจว่าอ่านอย่างเดียว ห้ามลองยิงดู
4. **ห้ามแก้ `peak-tools.json` หรือ `tools:` ของ agent ให้เอง** — บอกผู้ใช้ให้เติม
5. **ห้ามรายงานว่า "ไม่มีข้อมูล" เมื่อความจริงคือถูก deny หรือไม่มีสิทธิ์**
6. **ห้ามดึงข้อมูลเมื่อกิจการปลายทางไม่ตรงกับ `client-profile.md`**
7. **ห้ามปรับตัวเลขให้การตรวจยอดผ่าน**
8. **ห้ามเขียนโค้ดวาดไฟล์ขึ้นมาใหม่นอกสคริปต์** และห้ามเปลี่ยนไปออก `.csv` เงียบ ๆ
9. **ห้ามเขียนไฟล์นอก `<งวด>/output/`**
10. **ห้ามพยากรณ์ ประมาณการ หรือให้คำแนะนำทางธุรกิจ**
11. ไฟล์ผลมีข้อมูลทางการเงินของลูกค้าตาม PDPA — เก็บในโฟลเดอร์ลูกค้าบนเครื่องสำนักงานเท่านั้น

# หัวข้อที่ SKILL.md ต้องมี เรียงตามนี้

1. ชื่อ + ประโยคว่าอ่านอย่างเดียว + ต้องใช้คู่กับ plugin หลัก
2. ตารางกฎที่ hook บังคับ (🔒) + **กล่องเตือนเรื่อง learn-mode** + กฎที่ต้องใช้วิจารณญาณ
3. ขอบเขต — รองรับ / ไม่รองรับ (ไม่เขียน ERP, ไม่รวมหลายกิจการ, ไม่แปลงสกุลเงิน,
   ไม่พยากรณ์, ไม่ใช่ตัวเลขยื่นภาษี)
4. Step 0 สำรวจ tool → หัวข้อเมื่อถูก deny → Step 1–6
5. Edge cases
6. ข้อจำกัดและสิ่งที่ผู้ใช้ต้องตรวจเอง

หัวข้อ 6 ต้องพูดตรง ๆ ว่า: ตัวเลขคือสิ่งที่ ERP รายงาน ณ เวลาที่ดึง **ไม่ใช่งบการเงินที่ตรวจสอบแล้ว** ·
**ชุด tool ยังไม่ได้ยืนยันกับ endpoint จริง — รันสองครั้งต่างเวลาอาจได้จำนวนชีตไม่เท่ากัน
และชีตที่มาของข้อมูลคือที่ที่บอกว่าครั้งนี้ได้อะไรมาและขาดอะไรเพราะอะไร** ·
ไม่ได้กระทบยอดกับเอกสารต้นทางหรือ statement ธนาคาร · ช่อง `ดึงไม่ได้` ห้ามอ่านเป็นศูนย์ ·
อัตราส่วนเป็นค่าที่คำนวณต่อ · **ไม่ตรวจความถูกต้องทางบัญชีและไม่ตรวจจับการทุจริต** ·
การตรวจยอดข้ามแหล่งไม่ได้บอกว่าฝั่งไหนถูก
