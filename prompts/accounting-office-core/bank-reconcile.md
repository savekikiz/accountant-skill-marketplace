# ความรู้โดเมนที่ต้องเขียนลงใน skill

## ก. ลำดับการจับคู่ — ต้องเขียนเป็นลำดับ ห้ามให้เลือกอิสระ

จับคู่ทีละลำดับ รายการที่จับคู่ได้แล้วออกจากกองทันที ไม่ถูกพิจารณาซ้ำในลำดับถัดไป

1. **1:1 ยอดตรง** — ด้านเดียวกัน · ผลต่างยอด ≤ เกณฑ์ · วันที่ห่าง ≤ เกณฑ์
   ถ้ามีชื่อผู้โอน/ผู้รับทั้งสองฝั่ง ใช้ความคล้ายของชื่อช่วยตัดสินเมื่อมีคู่แข่งหลายคู่
2. **1:1 ที่ผลต่างเป็นภาษีหัก ณ ที่จ่าย** — เกิดเมื่อผู้จ่ายหัก WHT ก่อนโอน เงินเข้าจึงน้อยกว่ายอดตามใบแจ้งหนี้
   สูตร: ยอดใน GL − ยอดใน statement = ยอด WHT
   แล้วตรวจว่ายอด WHT ≈ ยอดก่อน VAT × อัตรามาตรฐาน ภายในเกณฑ์ผลต่าง
   - ถ้า GL มีคอลัมน์ WHT แยกอยู่แล้ว ให้ใช้ค่านั้นตรง ๆ ห้ามอนุมานจากผลต่าง
   - ต้องลองทุกอัตราที่ระบุในค่าตั้ง ไม่ใช่เดาอัตราเดียว
   - ต้องบันทึกอัตราและยอดที่สันนิษฐานไว้ในคอลัมน์หมายเหตุทุกคู่
3. **1:หลายรายการ** — หลายรายการฝั่งหนึ่งรวมได้เท่ายอดเดียวในอีกฝั่ง
   ต้องอยู่ในช่วงวันที่ที่ยอมรับ · ผลรวมต่าง ≤ เกณฑ์ · ไม่เกินจำนวนรายการสูงสุดต่อกลุ่ม
   ถ้าไม่ลงตัว ให้ลองหัก WHT อัตรามาตรฐานแล้วคำนวณใหม่
4. **ค้างกระทบยอด** — ที่เหลือทั้งหมด ต้องจัดประเภทให้ทุกบรรทัด

ข้อบังคับของการจับคู่: **ห้ามจับคู่ข้ามด้าน** (รับกับจ่าย)

## ข. ประเภทรายการค้างกระทบยอด — ต้องเป็นตารางใน skill

| ประเภท | ลักษณะ | ปกติหรือไม่ |
|---|---|---|
| เช็คจ่ายที่ยังไม่ขึ้นเงิน | มีใน GL ด้านจ่าย ไม่มีใน statement | ปกติ |
| เงินฝากระหว่างทาง | มีใน GL ด้านรับ ไม่มีใน statement | ปกติ |
| ค่าธรรมเนียมธนาคาร | มีใน statement ด้านจ่าย ไม่มีใน GL | ปกติ — ต้องบันทึกเพิ่ม |
| ดอกเบี้ยรับ | มีใน statement ด้านรับ ไม่มีใน GL | ปกติ — ต้องบันทึกเพิ่ม |
| ภาษีหัก ณ ที่จ่ายจากดอกเบี้ย | ยอดเล็ก ด้านจ่ายใน statement | ปกติ |
| เช็คคืน | รายการกลับด้านในวันใกล้กัน | ต้องตรวจ |
| ไม่เข้าประเภทใดเลย | | ต้องสอบสวน |

## ค. การเตรียมข้อมูลก่อนจับคู่

- วันที่: ทำให้เป็นรูปแบบเดียวกัน และ **แปลง พ.ศ./ค.ศ. ให้ตรงกันทั้งสองฝั่ง**
- จำนวนเงิน: ตัดคอมมา เป็นทศนิยม 2 ตำแหน่ง ตรวจว่าเป็นบาทไม่ใช่สตางค์
- แยกกองด้านรับกับด้านจ่ายออกจากกันก่อนจับคู่
- ต้องให้ผู้ใช้ยืนยันคอลัมน์ที่ระบบเจอทั้งสองฝั่งก่อนเริ่ม (วันที่ / จำนวนเงิน / คำอธิบาย / ด้าน / WHT ถ้ามี)
- ต้องยืนยันยอดยกมาต้นงวดของทั้งสองฝั่ง — **ถ้าต้นงวดไม่ตรงกันอยู่แล้ว ให้หยุดและแจ้งผู้ใช้ก่อน**
  เพราะกระทบยอดงวดนี้ไม่มีความหมายถ้ายกมาผิด
- ถ้า statement เป็น PDF ต้อง extract เป็นตารางก่อน และแนะนำให้ขอ .xlsx/.csv จากธนาคารถ้ามี

## ง. Edge case ที่ต้องมีหัวข้อรองรับใน skill

WHT หลายอัตราปนกันในงวดเดียว · รายการข้ามเดือน/ข้ามปี · โอนระหว่างบัญชีของกิจการเอง (อย่านับซ้ำ) ·
รายการกลับรายการ/ยอดติดลบ · รูปแบบวันที่สองฝั่งไม่เหมือนกัน · หลายรายการยอดเท่ากันในวันเดียวกัน ·
ค่าธรรมเนียมรวมอยู่ในบรรทัดเดียวกับยอดโอน · statement ที่ export มาไม่ครบงวด

# ข้อกำหนดผลลัพธ์ที่ skill ต้องผลิต

ไฟล์ Excel หนึ่งไฟล์ ประกอบด้วย

1. **sheet รายการกระทบยอด** — หนึ่งบรรทัดต่อหนึ่งคู่/หนึ่งรายการค้าง มีคอลัมน์ฝั่ง GL (วันที่ คำอธิบาย
   จำนวนเงิน WHT), ฝั่ง statement (วันที่ คำอธิบาย จำนวนเงิน), สถานะ, รหัสกลุ่ม (สำหรับ 1:หลาย),
   ด้าน, ผลต่าง, ประเภทรายการค้าง, หมายเหตุ — ระบายสีตามสถานะที่ค่าตั้งกำหนด
2. **sheet งบกระทบยอด** — รูปแบบที่ยื่นผู้สอบบัญชีได้ สองขาแล้วลงท้ายด้วยผลต่างคงเหลือ:

   ยอดตาม Bank Statement สิ้นงวด → บวกเงินฝากระหว่างทาง → หักเช็คจ่ายที่ยังไม่ขึ้นเงิน
   → บวก/หักรายการอื่น = ยอดที่ปรับแล้ว

   ยอดตาม GL สิ้นงวด → บวกดอกเบี้ยรับที่ยังไม่บันทึก → หักค่าธรรมเนียมที่ยังไม่บันทึก
   → บวก/หักรายการอื่น = ยอดที่ปรับแล้ว

   ผลต่างคงเหลือ (ต้องเป็น 0)
3. **sheet สรุป** — หัวไฟล์ระบุชื่อ skill, ลูกค้า, บัญชี, งวด, วันที่สร้าง + จำนวนและ % ของแต่ละสถานะ
   + ยอดรวมสองฝั่ง + รายการที่ต้องบันทึกเพิ่มใน GL
4. **sheet ข้อมูลต้นฉบับสองฝั่ง** — เพื่อให้ตรวจย้อนกลับได้

และต้องสรุปในแชตหลังทำเสร็จ: % ที่จับคู่ได้ · จำนวนรายการค้างแยกตามประเภท · ผลต่างคงเหลือ ·
รายการที่ยังอธิบายไม่ได้เรียงตามยอดเงิน · รายการที่ต้องบันทึกเพิ่มใน GL

# กฎห้าม — ต้องเขียนลงใน skill เป็นหัวข้อของตัวเอง

1. **ห้ามเดา** อ่านไม่ออกหรือไม่แน่ใจ ให้บันทึกว่าไม่แน่ใจแล้วถามผู้ใช้ ห้ามเติมค่าให้ดูสมบูรณ์
2. **ห้ามบังคับให้ผลต่างคงเหลือเป็นศูนย์** ด้วยรายการ "ผลต่างอื่น ๆ" ที่ไม่มีคำอธิบาย
   ถ้าไม่เป็นศูนย์ ให้แสดงตัวเลขจริงพร้อมข้อความว่ายังกระทบยอดไม่ครบ
3. **ห้ามจับคู่ข้ามด้าน** และห้ามจับคู่แบบหลายต่อหลาย
4. **ห้ามบันทึกรายการปรับปรุงเข้า ERP ให้** — skill นี้ชี้ว่าอะไรไม่ตรงเท่านั้น
5. ถ้าผู้ใช้ไม่ระบุโฟลเดอร์ลูกค้าหรืองวด ให้ถามก่อน ห้ามเดา ห้ามไล่สแกนทั้งเครื่อง
6. ข้อมูลเดินบัญชีเป็นข้อมูลอ่อนไหวตาม PDPA — ระบุว่าทำงานบนเครื่องสำนักงานเท่านั้น

# หัวข้อที่ SKILL.md ต้องมี เรียงตามนี้

1. ชื่อและประโยคเดียวว่า skill นี้ตอบคำถามอะไร
2. กฎที่ต้องใช้วิจารณญาณ (ถ้าโหมดกฎบังคับเปิด ให้เพิ่มตารางกฎที่ hook บังคับไว้ก่อนหัวข้อนี้)
3. ขอบเขต — แยก "รองรับ" กับ "ไม่รองรับ" เป็นสองรายการ
4. ขั้นตอนการทำงานเป็น Step ที่เดินตามได้ ตั้งแต่โหลดบริบทถึงสรุปในแชต
5. Edge case ที่เจอจริง เป็นรายการนับได้
6. ข้อจำกัดและสิ่งที่ผู้ใช้ต้องตรวจเอง

หัวข้อ 6 ต้องพูดตรง ๆ อย่างน้อยว่า: สถานะ "ตรง" หมายถึงเข้าเงื่อนไขที่ตั้งไว้ ไม่ใช่ถูกต้องทางบัญชี ·
1:1 อาจได้คู่ผิดเมื่อมีหลายรายการยอดเท่ากัน · 1:หลายรายการเสี่ยง false positive สูงที่สุด ·
การสันนิษฐาน WHT จากผลต่างเป็นการอนุมานที่ต้องตรวจกับหนังสือรับรองตัวจริง ·
ความคล้ายของชื่อไม่ใช่หลักฐาน · การอ่าน PDF อาจได้ตัวเลขเพี้ยน · ไม่ตรวจจับการทุจริต

## แบบฝึกหัดปรับแต่ง

แก้ทีละข้อ รันใหม่ แล้วเทียบกับผลก่อนหน้า

| # | แก้ค่าตั้งเป็น | สิ่งที่ควรเห็นใน skill ที่ได้ | บทเรียน |
|---|---|---|---|
| 1 | ผลต่างที่ยอมรับ `20 บาท` | ต้องมีคำเตือนว่ากินค่าธรรมเนียมเข้าไปในคู่ที่ "ตรง" | เกณฑ์หลวมซ่อนรายการที่ต้องบันทึกเพิ่ม |
| 2 | อัตรา WHT เหลือ `3%` เดียว | ลำดับ 2 สั้นลง และควรเตือนว่าจะพลาดกรณี 1%/5% | ตัดสิ่งที่ไม่ใช้ = ผิดน้อยลง แต่ครอบคลุมน้อยลง |
| 3 | จำนวนรายการต่อกลุ่ม `10` | ต้องมีคำเตือนเรื่องผลรวมบังเอิญตรงที่เพิ่มขึ้นมาก | ความยืดหยุ่นแลกมาด้วย false positive |
| 4 | ตัด `.pdf` ออกจากไฟล์เข้า | ขั้นตอน extract PDF หายไป skill สั้นลงชัดเจน | ขอบเขตแคบ = skill อ่านง่ายและแม่นกว่า |
| 5 | โหมดกฎบังคับ `เปิด` | ต้องมีตารางกฎที่ hook บังคับอยู่ต้นไฟล์ | ความต่างระหว่าง "ขอ" กับ "บังคับด้วย hook" |
| 6 | ช่วงวันที่ `±0 วัน` | ต้องเตือนว่ารายการข้ามเดือนจะกลายเป็นค้างทั้งหมด | เกณฑ์แน่นเกินไปก็ใช้งานไม่ได้ |

**โจทย์ต่อยอด** — เพิ่มเข้าไปในบล็อกค่าตั้งเอง แล้วดูว่า skill รับมือไหวไหม

- รองรับหลายบัญชีธนาคารในการรันครั้งเดียว (ตัวจริงตั้งใจไม่รองรับ — ลองคิดว่าทำไม)
- เพิ่มบัญชีสกุลเงินต่างประเทศและอัตราแลกเปลี่ยน
- ให้ออกร่างรายการปรับปรุงเป็น journal entry ด้วย (แต่ยังไม่บันทึกเข้า ERP)

## ตรวจว่า skill ที่ได้ใช้งานได้จริง

1. เทียบกับตัวจริงทีละหัวข้อ — ดูว่า **ตรรกะและตัวเลข** ตรงไหม ไม่ต้องดูถ้อยคำ
2. ให้คะแนนด้วย skill `skill-evaluator` (static review + rubric)
3. ทดสอบกับข้อมูลสมมติที่ฝังกรณียากไว้ตั้งแต่ต้น — อย่างน้อย 5 กรณีนี้:

| กรณีทดสอบ | คำตอบที่ถูก |
|---|---|
| GL 10,000 / statement 9,700 วันเดียวกัน | ตรง 1:1 (WHT 3% = 300) |
| GL 3 รายการ 1,000+2,000+3,000 / statement 6,000 | ตรง 1:หลาย กลุ่มเดียว |
| GL ลง 31 ม.ค. / statement 2 ก.พ. ยอดเท่ากัน | ตรง 1:1 (ถ้าเกณฑ์ ±3 วัน) |
| statement มีรายการ 107 บาท ไม่มีใน GL | ค้างกระทบยอด = ค่าธรรมเนียมธนาคาร |
| GL 5,000 สองรายการวันเดียวกัน / statement 5,000 หนึ่งรายการ | จับคู่ได้ 1 คู่ อีกรายการค้าง และต้องเตือนว่าอาจจับผิดคู่ |

ถ้ากรณีสุดท้ายผ่านโดย **ไม่มีคำเตือน** ถือว่า skill ยังไม่ผ่าน — อันตรายที่สุดของงานนี้คือ
ผลลัพธ์ที่ดูลงตัวแต่จับคู่ผิดคู่
