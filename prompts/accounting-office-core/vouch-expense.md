# ความรู้โดเมนที่ต้องเขียนลงใน skill

## ก. ข้อมูลที่ต้องดึงจากเอกสารต้นฉบับ 1 ใบ

เลขที่เอกสาร · วันที่ออกเอกสาร (บันทึกไว้ว่าเป็น พ.ศ. หรือ ค.ศ.) · ชื่อผู้ขาย ·
เลขผู้เสียภาษีผู้ขาย 13 หลัก (ถ้ามี) · ยอดก่อน VAT · VAT · ยอดรวมทั้งสิ้น ·
ประเภทเอกสาร (ใบกำกับเต็มรูป / อย่างย่อ / ใบเสร็จ / ใบแจ้งหนี้) · ชื่อไฟล์

แล้วสร้าง index จากเลขที่เอกสารที่ normalize แล้ว → **เป็น list ไม่ใช่ค่าเดียว** เพราะเลขที่ซ้ำกันได้

เอกสารใบเดียวที่ถูกสแกนเป็นหลายไฟล์/หลายหน้า ให้รวมเป็นใบเดียวโดยใช้ **ยอดจากหน้าสรุป**
ไม่ใช่บวกยอดทุกหน้า

## ข. ลำดับการจับคู่

**ระดับ 1 — เลขที่เอกสาร** หลัง normalize (ตัดช่องว่าง ขีด ทับ แล้วทำเป็นตัวพิมพ์ใหญ่)
เพราะเลขเดียวกันเขียนได้หลายแบบ เช่น `ES-6807001` กับ `ES6807001`

**ระดับ 1.5 — จับคู่สำรอง** ใช้เมื่อเลขที่เอกสารอ่านไม่ได้หรือไม่ตรง
ต้องเข้าเงื่อนไข **ครบทั้ง 3 ข้อ**: ยอดรวมตรงตามเกณฑ์ · วันที่อยู่ในช่วงที่ยอมรับ · ชื่อผู้ขายคล้ายกัน
ถ้าเข้าเงื่อนไข → สถานะแยกออกมาให้เห็นว่าจับคู่ด้วยวิธีนี้ และ **ต้องให้คนยืนยันทุกใบ**

**ระดับ 2 — เทียบยอด**
ยอดในรายการ = ยอดก่อน VAT + VAT (หรือคอลัมน์ยอดรวมถ้ามี)
ผลต่าง = |ยอดในรายการ − ยอดรวมในเอกสาร| แล้วจัดระดับตามเกณฑ์ในค่าตั้ง
**ก่อนสรุปว่า "ยอดต่าง" ให้ลองตรวจว่าผลต่างเท่ากับ WHT อัตรามาตรฐานของยอดก่อน VAT หรือไม่**
ถ้าใช่ ให้ระบุไว้ในเหตุผล — ผลต่างที่อธิบายได้ ไม่ใช่ปัญหา

**ระดับ 3 — ตรวจเพิ่ม**
วันที่ห่างเกินเกณฑ์ → หมายเหตุ cut-off · เลขที่ซ้ำในไฟล์รายการ → เสี่ยงบันทึกซ้ำ ·
เลขที่ซ้ำในโฟลเดอร์เอกสาร → เสี่ยงใช้เอกสารเดียวลง 2 ครั้ง ·
ชื่อผู้ขายไม่ใกล้เคียงกันทั้งที่เลขที่เอกสารตรง → หมายเหตุให้คนดู

## ค. การแมปผลเข้า audit assertion — ต้องเป็นตารางในไฟล์

| ผลที่เจอ | assertion ที่กระทบ |
|---|---|
| ไม่พบเอกสาร | Existence / Occurrence |
| ยอดต่าง | Accuracy |
| วันที่ห่างข้ามงวด | Cut-off |
| รายการซ้ำ / เอกสารซ้ำ | Accuracy (บันทึกซ้ำ) |
| เอกสารในโฟลเดอร์ที่ไม่มีรายการรองรับ | Completeness |

ตารางนี้สำคัญเพราะมันบอกผู้ใช้ว่าผลแต่ละแบบ "หมายความว่าอะไรในเชิงการตรวจสอบ"
ไม่ใช่แค่ตัวเลขที่ไม่ตรง

## ง. Edge case ที่ต้องมีในไฟล์

ใบเสร็จร้านค้าปลีกที่ยอดไม่ตรงเพราะมีสินค้า Non-VAT ปน (ใช้ ยอดก่อน VAT + VAT เทียบ ไม่ใช่ × 1.07) ·
เลขที่เอกสารรูปแบบต่างกัน · ได้แต่ใบส่งของ ใบกำกับมาทีหลัง (สถานะพบ แต่ระบุว่าเอกสารที่พบไม่ใช่ใบกำกับภาษี) ·
ใบแจ้งหนี้ใบเดียวแต่ลงหลายรายการ (ถูกได้ แต่ผลรวมต้องเท่ายอดในเอกสาร ไม่งั้น flag) ·
วันที่ในเอกสารเป็น พ.ศ. แต่ในไฟล์เป็น ค.ศ. (normalize ก่อน อย่าปล่อยให้ต่างกัน 543 ปี) ·
ภาพเบลอ/ถ่ายเอียง (ต้องตรวจมือ พร้อมระบุว่าอ่านส่วนไหนไม่ออก) · เอกสารภาษาอังกฤษล้วน

# ข้อกำหนดผลลัพธ์

1. **sheet VOUCH** = ทุกคอลัมน์เดิมของไฟล์ต้นทาง **ต่อท้าย**ด้วย 4 คอลัมน์ใหม่:
   - `vouch_status` — 6 สถานะ: พบ / พบ—ยอดต่าง / พบ—เอกสารซ้ำ / พบ(จับคู่จากยอด+วันที่) / ไม่พบเอกสาร / ต้องตรวจมือ
   - `vouch_reason` — พบในไฟล์ไหน วันที่และผู้ขายในเอกสาร ยอดที่เทียบ ผลต่างและสาเหตุที่สันนิษฐาน
   - `vouch_file` — ชื่อไฟล์เอกสารที่จับคู่ได้
   - `vouch_diff` — ผลต่างเป็นตัวเลข (บวก = รายการสูงกว่าเอกสาร)
   ระบายสีตามสถานะ · **ทุกแถวต้องมีค่าใน vouch_status และ vouch_reason ห้ามเว้นว่าง**
2. **sheet SUMMARY** — หัวไฟล์ (plugin/เวอร์ชัน ลูกค้า งวด วันที่) + จำนวนและ % ของแต่ละสถานะ
   + ยอดรวมที่ตรวจ + ยอดรวมของรายการที่ยังมีปัญหา
   + **รายการเอกสารในโฟลเดอร์ที่ไม่ถูกจับคู่กับรายการใดเลย** (อาจแปลว่ายังลงบัญชีไม่ครบ)

สรุปในแชต: จำนวนและยอดรวมของแต่ละสถานะ · จำนวนเอกสารที่ยังไม่มีรายการรองรับ ·
ประเด็นที่ควรตามก่อนเรียงตามยอดเงิน · แล้วปิดท้ายด้วยตาราง assertion

# ขั้นตอนที่ต้องมีก่อนเริ่มจับคู่

1. อ่าน client-profile.md และ mapping-overrides.md
2. ตรวจว่าไฟล์รายการเป็น format ไหน
3. **แสดงสรุปให้ผู้ใช้ยืนยันก่อนเริ่ม** — จำนวนรายการ ช่วงวันที่ ยอดรวม และตัวอย่าง 3 แถวแรก
4. ยืนยัน column mapping: เลขที่เอกสาร / วันที่ / ยอดก่อน VAT / VAT / ยอดรวม / ชื่อผู้ขาย
5. ถามว่าเอกสารต้นฉบับอยู่ที่ไหนถ้าไม่ใช่โฟลเดอร์มาตรฐาน
6. **ถ้าช่วงวันที่ในไฟล์ไม่ตรงกับงวดที่ผู้ใช้บอก ให้ทักก่อน อย่าเดินหน้าเงียบ ๆ**

# กฎห้าม — ต้องเขียนเป็นหัวข้อของตัวเอง

1. **ห้ามเดา** อ่านเอกสารไม่ออกให้ออกผลเป็น "ต้องตรวจมือ" พร้อมระบุส่วนที่อ่านไม่ออก
2. **ห้ามแก้ไขไฟล์ต้นทาง** — อ่านอย่างเดียว ออกไฟล์ผลใหม่ ถ้าต้องแก้ให้ผู้ใช้แก้แล้วรันซ้ำ
3. **ห้ามเลื่อนสถานะขึ้นเพราะ "น่าจะใช่"** — การจับคู่สำรองต้องแสดงเป็นสถานะของตัวเองเสมอ
4. **ห้ามตัดสินว่ารายจ่ายหักภาษีได้หรือไม่ได้ตามมาตรา 65 ตรี** และไม่ตัดสินสิทธิขอคืนภาษีซื้อ
5. **ห้ามลดระดับความรุนแรงของผลที่ subagent รายงานมา** ถ้าส่งให้ tax-compliance-checker ตรวจ
   ต้องคงการแบ่ง ผิดแน่ / น่าสงสัย / ต้องถามเพิ่ม ไว้ตามเดิม
6. ไม่ระบุโฟลเดอร์ลูกค้า/งวด → ถามก่อน
7. เอกสารมีข้อมูลส่วนบุคคลตาม PDPA — ทำงานบนเครื่องสำนักงานเท่านั้น

# หัวข้อที่ SKILL.md ต้องมี เรียงตามนี้

1. ชื่อ + ทิศทางของงาน (สมุดบัญชี → เอกสาร)
2. กฎที่ต้องใช้วิจารณญาณ
3. ขอบเขต — รองรับ / ไม่รองรับ (ไม่ทำฝั่งรายได้ ไม่ตัดสินภาษี ไม่แก้ไฟล์ต้นทาง)
4. ขั้นตอนการทำงานเป็น Step รวมขั้นส่งต่อ subagent แบบถามผู้ใช้ก่อน
5. Edge cases
6. ข้อจำกัดและสิ่งที่ผู้ใช้ต้องตรวจเอง

หัวข้อ 6 ต้องพูดตรง ๆ ว่า: "พบ" แปลว่าจับคู่ได้ตามเงื่อนไขที่ตั้งไว้ ไม่ใช่รายการถูกต้อง ·
การจับคู่สำรองเสี่ยง false positive สูง ต้องเปิดดูทุกใบ · ไม่ตรวจว่าเอกสารเป็นของแท้
ไม่ตรวจลายเซ็นอนุมัติ **ไม่ตรวจจับการทุจริต** · ไม่ตรวจว่ารายจ่ายเกี่ยวกับกิจการจริงหรือไม่
