# ความรู้โดเมนที่ต้องเขียนลงใน skill

## ก. ตารางกฎตรวจ — ต้องมีคอลัมน์ รหัส / กฎ / เงื่อนไขที่ถือว่าผิด / ระดับ

หนึ่งแถวมีได้หลาย flag — ต้องตรวจครบทุกกฎกับทุกแถวแล้วเก็บ flag สะสม ห้ามหยุดที่ flag แรก

| รหัส | ตรวจอะไร | ระดับ |
|---|---|---|
| TAXID_LEN | เลขผู้เสียภาษีผู้ขายไม่ครบ 13 หลักหลังลบช่องว่าง/ขีด | ต้องแก้ |
| TAXID_SUM | checksum 13 หลักไม่ผ่าน | ต้องแก้ |
| VAT_MATH | |ยอดก่อน VAT × อัตรา − VAT| เกินค่าคลาดเคลื่อน | ต้องแก้ |
| VAT_SUM | ยอดก่อน VAT + VAT ≠ ยอดรวม | ต้องแก้ |
| VAT_RATE | อัตราที่คำนวณได้ไม่ใช่ 0% หรือใกล้อัตรามาตรฐาน | ต้องดู |
| DATE_ERA | ปีอยู่นอกช่วงที่สมเหตุสมผล (พ.ศ./ค.ศ. สลับกัน) | ต้องแก้ |
| DATE_PERIOD | วันที่เอกสารไม่อยู่ในงวดที่กำลังทำ | ต้องดู |
| DATE_AMBIG | วัน/เดือนกำกวม (ทั้งคู่ ≤ 12 และรูปแบบไม่ชัด) | ต้องแก้ |
| DOC_DUP | เลขที่เอกสาร + เลขผู้เสียภาษีผู้ขาย ซ้ำในงวดเดียวกัน | ต้องแก้ |
| DOC_MISSING | ไม่มีเลขที่เอกสาร | ต้องแก้ |
| AMT_ZERO | ยอดรวม ≤ 0 | ต้องแก้ |
| AMT_OUTLIER | ยอดสูงกว่า median เกินเกณฑ์ | ต้องดู |
| VAT_ABBREV | ใบกำกับภาษีอย่างย่อแต่มีการขอคืน VAT | ต้องดู |
| NO_VAT_CLAIM | client-profile ระบุไม่จด VAT แต่มีแถวที่แยก VAT | ต้องดู |
| LOW_CONF | ไฟล์มีคอลัมน์ confidence และค่าต่ำกว่าเกณฑ์ | ต้องดู |

หลักการแบ่งระดับที่ต้องอธิบายไว้ในไฟล์:
**ต้องแก้ = ข้อมูลผิดแน่ ๆ ในเชิงคณิตศาสตร์หรือโครงสร้าง** · **ต้องดู = อาจถูกก็ได้ ต้องใช้ดุลพินิจ**
ถ้าเอาเรื่องดุลพินิจไปไว้ที่ "ต้องแก้" คนตรวจจะเจอ false positive จนเลิกเชื่อไฟล์

## ข. references/tax-id-checksum.md ต้องมี

สูตร: ให้ d[0]…d[12] คือตัวเลขแต่ละหลักจากซ้าย
sum = Σ d[i] × (13 − i) สำหรับ i = 0..11 แล้ว check digit = (11 − (sum mod 11)) mod 10
ต้องตรงกับ d[12] — พร้อมตัวอย่างคำนวณทีละขั้น 1 เลข และระบุว่าบุคคลธรรมดาใช้สูตรเดียวกัน
ปิดท้ายด้วยข้อจำกัด: checksum ผ่าน = เลขมีโครงสร้างถูก ไม่ได้แปลว่าเป็นเลขของผู้ขายรายนั้นจริง

## ค. references/vat-rules.md ต้องมี

อัตรา (ทั่วไป 7% ตาม ป.รัษฎากร ม.80 + พ.ร.ฎ. ลดอัตราที่ต่ออายุรายปี · ส่งออก/บริการใช้ในต่างประเทศ 0% ม.80/1) ·
ความต่างระหว่างใบกำกับภาษีเต็มรูป (ม.86/4) กับอย่างย่อ (ม.86/6) และผลต่อสิทธิขอคืนภาษีซื้อ ·
ระยะเวลาขอคืนภาษีซื้อย้อนหลัง 6 เดือน · กรณีสินค้ายกเว้น VAT ตาม ม.81 ·
บรรทัดบนสุดต้องระบุวันที่ตรวจสอบกฎครั้งล่าสุด ปีภาษีที่ใช้ และประโยคว่าต้องตรวจอัตราปัจจุบันที่ rd.go.th ก่อนใช้กับงวดอื่น

## ง. ขั้นตอนการทำงานที่ต้องเขียนเป็น Step

1. โหลดบริบท: อ่าน client-profile.md (ชื่อบริษัท เลขผู้เสียภาษี สถานะ VAT รอบบัญชี) และ mapping-overrides.md
   แล้ว **แสดงคอลัมน์ที่เจอในไฟล์ OCR ให้ผู้ใช้ยืนยัน mapping ก่อน** — คอลัมน์ไหนคือเลขที่เอกสาร วันที่
   ยอดก่อน VAT VAT ยอดรวม เลขผู้เสียภาษีผู้ขาย
2. ตรวจทุกกฎกับทุกแถว เก็บ flag สะสม
3. **เปิดภาพต้นฉบับซ้ำเฉพาะแถวระดับ "ต้องแก้"** แล้วเติมคอลัมน์ "ค่าที่ควรเป็น"
   อ่านไม่ออกให้เขียนว่า `อ่านไม่ออก` — การเดาตัวเลขให้ดูเรียบร้อยอันตรายกว่าการบอกว่าอ่านไม่ออก
4. ออกไฟล์ผล
5. สรุปในแชต แล้ว **ชี้ว่าควรแก้อะไรก่อนโดยเรียงตามยอดเงินที่เกี่ยวข้อง ไม่ใช่ตามจำนวนใบ**

## จ. Edge case ที่ต้องมีในไฟล์

ใบกำกับหลายหน้าที่ OCR แยกเป็นหลายแถว (รวมด้วยยอดหน้าสรุป ไม่ใช่บวกทุกหน้า) ·
สินค้า Non-VAT ปนในใบเดียวกัน (ยอดก่อน VAT × 1.07 ≠ ยอดรวม เป็นเรื่องปกติ ต้องดูช่องมูลค่ายกเว้นภาษีก่อน flag) ·
ส่วนลดท้ายเอกสาร (คำนวณ VAT จากยอดหลังหักส่วนลด) · ผู้ขายบุคคลธรรมดาไม่จด VAT (ไม่มี VAT คือถูกต้อง อย่า flag) ·
เอกสารข้ามงวด (flag ได้ แต่ไม่ใช่ความผิด — ภาษีซื้อขอคืนย้อนหลังได้ 6 เดือน) ·
ไฟล์ OCR ไม่มีคอลัมน์ confidence (ข้ามกฎนั้นแล้วระบุใน SUMMARY ว่าข้ามเพราะไม่มีข้อมูล)

# ข้อกำหนดผลลัพธ์

ไฟล์ Excel หนึ่งไฟล์:
1. **sheet EXCEPTIONS** — เฉพาะแถวที่มี flag คอลัมน์: แถวที่ในไฟล์ต้นทาง, ไฟล์ต้นฉบับ, ผู้ขาย, เลขที่เอกสาร,
   วันที่, ยอดรวม, รหัส flag (หลายรหัสคั่นด้วย `;`), ระดับ, ค่าที่ OCR อ่านได้, ค่าที่ควรเป็น,
   ผู้ตรวจแก้ (เว้นว่างให้คนกรอก), แก้แล้ว (เว้นว่างให้คนกรอก) — ระบายสีตามระดับ
2. **sheet SUMMARY** — หัวไฟล์ระบุชื่อ plugin/เวอร์ชัน ลูกค้า งวด วันที่สร้าง + จำนวนทั้งหมด/ผ่าน/ต้องแก้/ต้องดู
   + นับจำนวนแต่ละรหัส flag เรียงมากไปน้อย + ยอดเงินรวมของแถวที่ติด flag
3. **sheet CLEAN** — แถวที่ผ่านทุกกฎ พร้อมส่งต่อขั้นถัดไป

สรุปในแชตต้องมี: จำนวนเอกสารทั้งหมด / ผ่าน (%) / ต้องแก้ / ต้องดู + flag ที่เจอบ่อยสุด 3 อันดับ
พร้อมคำอธิบายสั้น ๆ ว่าแต่ละอันเกิดจากอะไร + path ไฟล์

# กฎห้าม — ต้องเขียนเป็นหัวข้อของตัวเอง

1. **ห้ามเดา** อ่านไม่ออกให้เขียนว่าอ่านไม่ออก ห้ามเติมค่าให้ดูสมบูรณ์
2. **ห้ามแก้ไฟล์ OCR ต้นทาง** — อ่านอย่างเดียว แล้วออกไฟล์ผลใหม่
3. **ห้าม OCR เอง** ถ้าไม่มีผล OCR ให้แจ้งผู้ใช้ว่าต้องรันเครื่องมือ OCR ก่อน
4. **ห้ามตัดสินว่ารายจ่ายเป็นรายจ่ายต้องห้ามตามมาตรา 65 ตรี** — เป็นดุลพินิจผู้ทำบัญชี
5. ไม่ระบุโฟลเดอร์ลูกค้า/งวด → ถามก่อน ห้ามเดา ห้ามไล่สแกนทั้งเครื่อง
6. เอกสารมีเลขผู้เสียภาษีซึ่งเป็นข้อมูลส่วนบุคคลตาม PDPA — ทำงานบนเครื่องสำนักงานเท่านั้น

# หัวข้อที่ SKILL.md ต้องมี เรียงตามนี้

1. ชื่อ + ประโยคเดียวว่า skill นี้ตอบอะไร และผลลัพธ์คือไฟล์เฉพาะแถวที่ต้องแก้มือ
2. กฎที่ต้องใช้วิจารณญาณ
3. ขอบเขต — รองรับ / ไม่รองรับ (ไม่ OCR เอง, ไม่ตัดสินรายจ่ายต้องห้าม, ไม่ตรวจว่าผู้ขายจด VAT จริง)
4. ขั้นตอนการทำงานเป็น Step
5. Edge cases
6. ข้อจำกัดและสิ่งที่ผู้ใช้ต้องตรวจเอง

หัวข้อ 6 ต้องพูดตรง ๆ อย่างน้อยว่า: แถวใน CLEAN คือ "ผ่านกฎที่ตั้งไว้" ไม่ใช่ "ถูกต้องแน่นอน" —
OCR อ่านยอดผิดเป็นตัวเลขที่ยังคำนวณลงตัวได้ · ไม่ตรวจว่าผู้ขายมีตัวตนจริง ·
**ไม่ตรวจใบกำกับภาษีปลอม** · checksum ผ่านไม่ได้แปลว่าเป็นเลขของผู้ขายรายนั้น ·
ไม่ตรวจว่าใบกำกับมีรายการครบตาม ม.86/4 ทุกข้อ

## แบบฝึกหัดปรับแต่ง

| # | แก้ค่าตั้งเป็น | สิ่งที่ควรเห็น | บทเรียน |
|---|---|---|---|
| 1 | ย้าย `DATE_PERIOD` เป็นระดับ "ต้องแก้" | ปริมาณแถวที่ต้องเปิดภาพซ้ำพุ่ง | เอกสารข้ามงวดเป็นเรื่องปกติ ไม่ใช่ความผิด |
| 2 | ค่าคลาดเคลื่อน VAT `±1.00 บาท` | `VAT_MATH` แทบไม่ขึ้นเลย | เกณฑ์หลวมเท่ากับปิดกฎนั้นทิ้ง |
| 3 | เกณฑ์ยอดผิดปกติ `3 เท่า` | flag เยอะจนต้องเตือนเรื่อง false positive | กฎที่ส่งเสียงดังเกินไปทำให้คนเลิกอ่านทั้งไฟล์ |
| 4 | ปิด sheet `CLEAN` | ขั้นถัดไป (`vouch-expense`) รับ input ต่อไม่ได้ | skill ในสายงานต้องส่งของให้กันได้ |
| 5 | ตัดกฎ `TAXID_SUM` ออก | reference checksum ไม่ถูกอ้างถึงเลย | reference ที่ไม่มีใครเรียกใช้คือ context ที่เสียเปล่า |
| 6 | เพิ่มกฎใหม่ `VENDOR_BLANK` (ไม่มีชื่อผู้ขาย) | ต้องเลือกระดับให้ถูก และเพิ่มในตารางนับของ SUMMARY | การเพิ่มกฎมีต้นทุน 3 จุด ไม่ใช่จุดเดียว |

## กรณีทดสอบ

| แถวทดสอบ | คำตอบที่ถูก |
|---|---|
| ยอดก่อน VAT 1,000 / VAT 70 / รวม 1,070 เลขผู้เสียภาษีถูก | ผ่าน อยู่ใน CLEAN |
| ยอดก่อน VAT 1,000 / VAT 7 / รวม 1,007 | `VAT_MATH` — ต้องแก้ |
| ยอดก่อน VAT 1,000 / VAT 70 / รวม 1,170 | `VAT_SUM` — ต้องแก้ |
| เลขผู้เสียภาษี 13 หลักแต่หลักสุดท้ายเพี้ยน | `TAXID_SUM` — ต้องแก้ |
| วันที่ `05/09/2026` ในงวดที่คาดว่าเป็น พ.ศ. | `DATE_ERA` — ต้องแก้ |
| ใบกำกับอย่างย่อจากร้านสะดวกซื้อ แยก VAT ขอคืน | `VAT_ABBREV` — ต้องดู |
| เอกสารเลขที่เดียวกัน ผู้ขายรายเดียวกัน 2 แถว | `DOC_DUP` ทั้งสองแถว — ต้องแก้ |
| ใบเสร็จร้านค้าที่มีทั้งสินค้า VAT และยกเว้น VAT | **ไม่ควร** flag `VAT_SUM` ทันที — ต้องดูช่องมูลค่ายกเว้นก่อน |
