# ความรู้โดเมนที่ต้องเขียนลงใน skill

## ก. สี่หลักการที่ทำให้รายงานนี้เชื่อถือได้ — ต้องปรากฏเป็นกฎ ไม่ใช่คำแนะนำ

1. **`ดึงไม่ได้` ไม่ใช่ `0`** — ศูนย์ปลอมหนึ่งช่องทำให้ทั้งไฟล์เชื่อไม่ได้
   และคนอ่านไม่มีทางรู้ว่าช่องนั้นว่างเพราะไม่มีรายการ หรือเพราะดึงไม่สำเร็จ
2. **ทุกตัวเลขมีที่มา** — บันทึกชื่อ tool, พารามิเตอร์ที่ส่งจริง, เวลาที่ดึง ของทุกบล็อกและทุก KPI
   แล้วออกเป็นชีตของตัวเอง ตัวเลขที่ไม่รู้ที่มา เอาไปใช้ตัดสินใจไม่ได้
3. **ตรวจยอดข้ามแหล่งแล้วไม่กลบ** — ไม่ตรงคือข้อมูล ไม่ใช่ข้อผิดพลาดที่ต้องทำให้หาย
   **ห้ามปรับตัวเลขฝั่งใดฝั่งหนึ่งให้ตรงกัน** หน้าที่คืออธิบายสาเหตุที่เป็นไปได้
4. **ห้ามคำนวณตัวเลขที่ ERP รายงานมาแล้วใหม่เอง** — ถ้าคำนวณต่อ (อัตราส่วน, % เปลี่ยนแปลง)
   ต้องกำกับว่าเป็นค่าที่คำนวณต่อ และถ้าไม่ตรงกับที่ ERP แสดง ให้เชื่อ ERP

## ข. ลำดับขั้นที่ต้องเขียนเป็น Step

- **Step 0 สำรวจ tool ที่มีจริง** — ดูรายชื่อ tool ของ MCP ที่โหลดอยู่จริงก่อนเรียกอะไร
  ชื่อใน reference เป็นชื่อที่พบในเวอร์ชันที่ทดสอบ **ห้ามเดาชื่อ tool**
  หา tool ของบล็อกไหนไม่เจอ → บล็อกนั้น `unavailable` พร้อมเหตุผล ไม่ใช่ข้ามเงียบ ๆ
  ชื่อ server โผล่ได้ทั้ง `mcp__flowaccount__…` และ `mcp__claude_ai_FlowAccount_MCP__…`
- **Step 1 ยืนยันกิจการปลายทาง** — อ่าน `client-profile.md` ยืนยันว่า ERP ตรง
  แล้วโหลดข้อมูลบริษัทจาก ERP มาแสดงเทียบกันเป็นบล็อกชัด ๆ (ชื่อ + เลขผู้เสียภาษีสองฝั่ง + ผลเทียบ)
  **ไม่ตรง → หยุดทันที** พร้อมเหตุผลว่า Dashboard ของกิจการผิดรายอ่านดูสมเหตุสมผลทุกบรรทัด
  และไม่มีใครจับได้จนกว่าจะเอาไปใช้ตัดสินใจ
  แล้วยืนยันงวดและงวดเทียบ **พร้อมพารามิเตอร์ที่จะส่งจริง**
- **Step 2 ตกลงขอบเขตชีตกับผู้ใช้** — การดึงทุกบล็อกกินเวลาและ token จริง
- **Step 3 ดึงข้อมูลลง data pack** — หนึ่งบล็อกหนึ่งการเรียก แล้วเขียนลงไฟล์ทันที
  ไม่กองผลดิบไว้ใน context · ผลลัพธ์ยาวให้สรุป/จัดอันดับก่อนเก็บ ·
  ดึงไม่ครบทุกหน้า → `partial` พร้อมบอกว่าได้กี่หน้าจากกี่หน้า
- **Step 4 ใส่รายการตรวจยอด** ตามค่าตั้ง
- **Step 5 รันสคริปต์** — ห้ามเขียนโค้ด openpyxl ขึ้นมาใหม่เอง
- **Step 6 สรุปในแชต** — **ยกสามอย่างจาก output ของสคริปต์มาด้วยทุกครั้ง**:
  บล็อกที่ดึงไม่ได้ · กราฟที่ไม่ได้วาง · การตรวจยอดที่ไม่ผ่าน
  อย่าปล่อยให้อยู่แต่ใน stdout ของสคริปต์

## ง. การแปลงงวด — ต้องเป็นตารางของตัวเอง

FlowAccount MCP รับค่าช่วงเวลาได้หลายรูป: คำสำเร็จ (`this_month`, `last_month`, `this_year`,
`last_year`, `last_3_months`), เดือนเดียว (`YYYY-MM`), ช่วงวันที่ (`YYYY-MM-DD_YYYY-MM-DD`),
วันเดียว (`YYYY-MM-DD`)

กฎที่ต้องเขียนไว้:
- **ส่งค่าช่วงเวลาเองทุกครั้ง** เพราะค่า default ของแต่ละ tool ไม่เหมือนกัน

- **ปี พ.ศ. → ค.ศ. ลบ 543 เสมอ** งวดที่สำนักงานเรียก `2569-09` คือ `2026-09`

  — ปี พ.ศ./ค.ศ. สลับกันคือวิธีที่ง่ายที่สุดที่จะได้รายงานของเดือนที่ไม่ได้ขอ

# สัญญาของ data pack — ส่วนที่สำคัญที่สุดของงานนี้

`references/dashboard-layout.md` คือข้อตกลงระหว่าง skill (คนดึงข้อมูล) กับสคริปต์ (คนวาดไฟล์)
สคริปต์ต้อง **ไม่รู้จัก ERP เลย** มันรู้แค่รูปของ JSON — นั่นคือเหตุผลที่สคริปต์ตัวเดียว
ใช้ได้กับ ERP หลายตัว

โครงที่ต้องนิยาม:

```
{
  "meta":   { erp, client, company_in_erp, period_label, compare_label, fetched_at, notes[] },
  "kpis":   [ { name, value, compare, higher_is_better, status, reason, source } ],
  "checks": [ { name, left, right, tolerance } ],
  "blocks": [ { id, sheet, title, status, reason, total_row, source,
                columns: [ { key, label, type, total, width } ], rows: [ {…} ] } ],
  "charts": [ { type, block, cat, values[], title, anchor } ]
}
```

สิ่งที่ต้องกำหนดให้ชัดในเอกสารสัญญา:
- `status` มี 3 ค่า: `ok` / `partial` / `unavailable` และ `reason` **บังคับ** เมื่อไม่ใช่ `ok`
- `columns[].type` มี 4 แบบ: `text` / `money` / `int` / `pct` (ค่า `pct` ส่งเป็นทศนิยม)
- `higher_is_better: false` สำหรับตัวเลขที่เพิ่มขึ้นแล้วแย่ (ค่าใช้จ่าย ลูกหนี้คงค้าง)
- ฝั่งใดของ `checks` ดึงไม่ได้ → ส่ง `null` แล้วผลต้องเป็น `ตรวจไม่ได้` **ไม่ใช่ `ผ่าน`**
- `charts` อ้าง `id` ของบล็อก และ `key` ของคอลัมน์ ไม่ใช่ค่าที่ก็อปมาแปะ
- **สิ่งที่สคริปต์ทำให้เอง ไม่ต้องส่งมาใน JSON**: หัวไฟล์ (ชื่อ plugin + เวอร์ชันจาก `plugin.json`),
  % เปลี่ยนแปลงของ KPI, แถวรวมแบบสูตร `SUM()`, สีตามสถานะ, ชีตที่มาของข้อมูล,
  การตรึงหัวตาราง, รูปแบบตัวเลข
- ปิดท้ายด้วย checklist ตรวจไฟล์ที่ได้ก่อนส่งผู้ใช้

# ข้อกำหนดของสคริปต์ build_dashboard.py

- อินเทอร์เฟซ: `python3 build_dashboard.py <data.json> --out <ไฟล์.xlsx> [--plugin-root <dir>]`
- **อ่านชื่อ+เวอร์ชันจาก `.claude-plugin/plugin.json`** (ผ่าน `CLAUDE_PLUGIN_ROOT` หรือไต่ path ขึ้นไป)
  แล้วเขียนเป็นหัวไฟล์ในเซลล์แรกของชีตแดชบอร์ด — **ห้าม hardcode เลขเวอร์ชัน**
  (หัวไฟล์นี้คือสิ่งที่ hook ของ plugin ตรวจหาในไฟล์ `.xlsx`)
- ไม่มี openpyxl → พิมพ์วิธีติดตั้งแล้วออกด้วย exit code 3 **ไม่ใช่ traceback**
- `status: "unavailable"` → เขียนแถวเดียวว่าดึงไม่ได้พร้อมเหตุผล พื้นสีเทา แล้วไม่วาดกราฟของบล็อกนั้น
- ช่องตัวเลขที่ไม่มีค่าใน `rows` → เขียน `ดึงไม่ได้` พื้นเทา **ไม่ใช่ 0 ไม่ใช่ช่องว่าง**
- แถวรวมต้องเป็น **สูตร `SUM()` จริง** ไม่ใช่ค่าคงที่ที่คำนวณไว้แล้ว
  (ผู้ใช้แก้ตัวเลขในตารางแล้วยอดรวมต้องขยับ)
- กราฟต้องอ้าง **เซลล์จริงในชีตของบล็อกนั้น** (cross-sheet reference) ไม่ใช่รูปภาพ
- ชีต **ที่มาของข้อมูล** สร้างจาก `source` ของทุกบล็อกและทุก KPI
- พิมพ์สรุปออก stdout: path, หัวไฟล์, จำนวนบล็อกที่ดึงไม่ได้/ไม่ครบ, กราฟที่ข้าม,
  การตรวจยอดที่ไม่ผ่าน + ประโยคเตือนว่าห้ามปรับตัวเลขให้ตรงกันเอง
- ไม่ต่อเน็ต ไม่รู้จัก ERP ไม่มี dependency นอก stdlib ยกเว้น openpyxl

# กฎห้าม — ต้องเขียนเป็นหัวข้อของตัวเอง

1. **ห้ามเดาตัวเลข และห้ามใส่ 0 แทนค่าที่ดึงไม่ได้**
2. **ห้ามเขียน แก้ อนุมัติ หรือลบอะไรใน ERP** — skill นี้อ่านอย่างเดียว
3. **ห้ามเดาชื่อ tool** — หาไม่เจอให้ทำบล็อกนั้นเป็น `unavailable`
4. **ห้ามดึงข้อมูลเมื่อกิจการปลายทางไม่ตรงกับ `client-profile.md`**
5. **ห้ามปรับตัวเลขให้การตรวจยอดผ่าน**
6. **ห้ามเขียนโค้ดวาดไฟล์ขึ้นมาใหม่นอกสคริปต์** และห้ามเปลี่ยนไปออก `.csv` เงียบ ๆ เมื่อไม่มี openpyxl
7. **ห้ามเขียนไฟล์นอก `<งวด>/output/`**
8. **ห้ามพยากรณ์ ประมาณการ หรือให้คำแนะนำทางธุรกิจ** — รายงานสิ่งที่เกิดขึ้นแล้ว
9. ไฟล์ผลมีข้อมูลทางการเงินของลูกค้าตาม PDPA — เก็บในโฟลเดอร์ลูกค้าบนเครื่องสำนักงานเท่านั้น

# หัวข้อที่ SKILL.md ต้องมี เรียงตามนี้

1. ชื่อ + ประโยคว่าอ่านอย่างเดียว ไม่เขียนกลับเข้า ERP + ต้องใช้คู่กับ plugin หลัก
2. ตารางกฎที่ hook บังคับ (🔒) + กฎที่ต้องใช้วิจารณญาณ
3. ขอบเขต — รองรับ / ไม่รองรับ (ไม่เขียน ERP, ไม่รวมหลายกิจการ, ไม่แปลงสกุลเงิน,
   ไม่พยากรณ์, ไม่ใช่ตัวเลขยื่นภาษี)
4. ขั้นตอน Step 0–6
5. Edge cases
6. ข้อจำกัดและสิ่งที่ผู้ใช้ต้องตรวจเอง

หัวข้อ 6 ต้องพูดตรง ๆ ว่า: ตัวเลขคือสิ่งที่ ERP รายงาน ณ เวลาที่ดึง **ไม่ใช่งบการเงินที่ตรวจสอบแล้ว** ·
ถ้าข้อมูลในระบบยังลงไม่ครบ Dashboard ก็ไม่ครบ และ skill ไม่มีทางรู้ว่าอะไรยังไม่ได้ลง ·
ไม่ได้กระทบยอดกับเอกสารต้นทางหรือ statement ธนาคาร · ช่อง `ดึงไม่ได้` ห้ามอ่านเป็นศูนย์ ·
อัตราส่วนเป็นค่าที่คำนวณต่อ ไม่ใช่ค่าจาก ERP · **ไม่ตรวจความถูกต้องทางบัญชีและไม่ตรวจจับการทุจริต** ·
การตรวจยอดข้ามแหล่งบอกได้แค่ว่าสองแหล่งตรงกันหรือไม่ **ไม่ได้บอกว่าฝั่งไหนถูก**
