# แนวคิดหลักที่ต้องสื่อให้ชัด

skill นี้เป็น **ขั้นสุดท้ายของสายงาน**: รายการที่ตรวจแล้ว → เอกสารใน FlowAccount สถานะรออนุมัติ
ไม่ใช่จุดเริ่ม — ถ้ารายการยังไม่ผ่านการตรวจ ต้องไม่บันทึก

และต้องระบุว่า plugin นี้ใช้คู่กับ plugin หลักของสำนักงาน ถ้ายังไม่ได้ติดตั้งให้บอกผู้ใช้ก่อน

# ความรู้โดเมนที่ต้องเขียนลงใน skill

## ก. Step 0 — สำรวจ tool ที่มีจริงก่อนเรียกอะไรเลย

ชื่อ tool ของ MCP เปลี่ยนได้ตามเวอร์ชัน ดังนั้น **ก่อนเรียก tool ใด ๆ ให้ดูรายชื่อ tool ของ MCP server
ที่โหลดอยู่จริงในเซสชันนี้ก่อน** ชื่อที่อ้างในเอกสารเป็นชื่อที่พบในเวอร์ชันที่ทดสอบไว้
ถ้าไม่ตรงให้ใช้ชื่อที่มีจริง และ **ห้ามเดาชื่อ tool** — หาไม่เจอให้หยุดแล้วแจ้งผู้ใช้

ถ้ายังไม่ได้เชื่อมต่อหรือ authorize MCP server ให้แจ้งผู้ใช้ทำก่อน — **ทำแทนไม่ได้**

## ข. Step 1 — ตรวจบริษัทปลายทางก่อนเขียนอะไรทั้งสิ้น

อ่านข้อมูลบริษัทที่เชื่อมต่ออยู่จาก FlowAccount แล้วแสดงเทียบให้ผู้ใช้เห็นเป็นบล็อกชัด ๆ:
ชื่อและเลขผู้เสียภาษีในระบบ เทียบกับใน client-profile.md แล้วสรุปว่าตรงหรือไม่ตรง

**ไม่ตรง → หยุดทันที อย่าบันทึกแม้แต่ใบเดียว** การบันทึกผิดบริษัทแก้ยากกว่าการรอ

แล้วตรวจสิทธิ์การสร้างเอกสารค่าใช้จ่าย ถ้าไม่มีสิทธิ์ → หยุด
และโหลดหมวดหมู่ค่าใช้จ่ายสดจากบริษัทนั้น — **ใช้ค่าที่ดึงสดเสมอ** reference เป็นแค่กฎการเลือก
และ snapshot อ้างอิง

## ค. Step 2 — คัดรายการ

รับ input จากไฟล์ผล vouch/OCR ของงวดนั้น แล้ว **คัดเฉพาะแถวที่ผ่าน**
รายการที่ยังติดสถานะ "ไม่พบเอกสาร" หรือ "ต้องแก้" → **ไม่บันทึก** แล้วรายงานแยกว่าข้ามกี่ใบเพราะอะไร

ตรวจคณิตศาสตร์ทุกใบก่อนไปต่อ: |ยอดก่อน VAT × 0.07 − VAT| ≤ ค่าคลาดเคลื่อน และ
ยอดก่อน VAT + VAT = ยอดรวม — ไม่ตรงให้ข้ามใบนั้นแล้วแจ้งผู้ใช้

## ง. Step 3 — กันเอกสารซ้ำ (ทำก่อนกัน vendor ซ้ำเสมอ)

ค้นด้วยเลขที่เอกสารของผู้ขายก่อน ไม่เจอให้ค้นด้วยชื่อ vendor + ยอดรวม
ซ้ำเมื่อครบเงื่อนไขตามค่าตั้ง → ข้ามใบนั้น แล้วรายงานว่าซ้ำกับเอกสารเลขที่อะไรในระบบ

## จ. Step 4 — กัน vendor ซ้ำ

ค้นตามลำดับในค่าตั้ง **ห้ามข้ามขั้น** แล้วจัดการตามผล:
เจอ 1 ราย → ใช้ id ของรายนั้น **ห้ามส่งชื่อ vendor คู่กับ id** ·
เจอหลายราย → เลือกรายที่มีเลขผู้เสียภาษีและที่อยู่ครบ แล้วแจ้งผู้ใช้ว่ามีซ้ำ ควรไปรวมในระบบ ·
ไม่เจอ → ทำเครื่องหมาย "vendor ใหม่" ใน preview ให้ผู้ใช้เห็นก่อน

ข้อที่ต้องเขียนให้ชัด: **MCP ไม่มี tool สร้าง contact แยก** — vendor ใหม่จะถูกสร้างอัตโนมัติ
ตอนสร้างเอกสารเมื่อส่งชื่อที่ยังไม่มีในระบบ นี่คือเหตุผลที่ต้องค้นให้ครบก่อน เพราะพลาดแล้วได้ vendor ซ้ำทันที

และ: **ที่อยู่ในเอกสารต่างจากที่อยู่ในระบบ ไม่ใช่เหตุผลให้สร้าง vendor ใหม่**

## ฉ. Step 5 — จับคู่หมวดหมู่

ลำดับความสำคัญ: mapping-overrides.md ของลูกค้า **ชนะ** ผังบัญชีของลูกค้า ชนะกฎ default
ความมั่นใจต่ำกว่าเกณฑ์ → ใส่เครื่องหมายเตือนใน preview พร้อมเสนอตัวเลือกสำรอง 2 ตัวให้ผู้ใช้เลือก

reference ของหมวดหมู่ต้องขึ้นต้นด้วยคำเตือนว่า id ของหมวดหมู่เป็นค่าเฉพาะของแต่ละบริษัท
ไม่ใช่ค่ากลาง ต้องดึงสดทุกครั้ง และ **ห้ามใช้ id จากลูกค้ารายอื่นข้ามกัน**

## ช. Step 6 — Preview (บังคับ)

ใช้ tool ตรวจสอบ/คำนวณแบบไม่เขียนจริง แล้วแสดง **ทั้งกองพร้อมกัน** เป็นตาราง:
ลำดับ · ไฟล์ · ผู้ขาย · เลขที่ · วันที่ · หมวดหมู่ · ยอดก่อน VAT · VAT · WHT · ยอดรวม · สถานะ
ตามด้วยยอดรวมทั้งกอง

และ **ต้องถามผู้ใช้ 2 ข้อนี้เสมอ ไม่มีค่า default**:
- VAT/ส่วนลดเป็นแบบแยกรายบรรทัด หรือท้ายเอกสาร
- ราคาในเอกสารรวม VAT แล้ว หรือยังไม่รวม

ก่อนแสดงให้ผู้ใช้ ให้ส่งตารางให้ผู้ตรวจอิสระก่อน แล้วแนบผลตรวจไปพร้อมตาราง
**ส่งให้แค่ path ของตาราง preview กับ path ของเอกสารต้นทาง ห้ามส่งเหตุผลว่าเราจับคู่หมวดหมู่แบบนั้นเพราะอะไร**
ผู้ตรวจที่รู้เหตุผลของผู้ทำจะเห็นด้วยโดยอัตโนมัติ และการตรวจจะไร้ความหมาย
ถ้าผู้ตรวจพบจุดไม่ผ่าน ให้แก้ที่ต้นทางแล้วตรวจใหม่ — **อย่าแสดงตารางที่รู้อยู่แล้วว่ามีจุดไม่ผ่าน**

รอคำยืนยันจากผู้ใช้ **ห้ามข้ามไปขั้นบันทึกเอง**

## ซ. Step 7 — บันทึกจริง และการรับมือ response ที่หลุด

สร้างเอกสารทีละใบ เก็บ id, เลขที่เอกสารในระบบ และค่าที่ response คืนมาสำหรับตรวจสถานะ

**ถ้า response ช้า หลุด หรือ timeout → ห้ามยิงซ้ำ** ให้ตรวจสถานะการสร้างเอกสารก่อน
เพราะ "ไม่มีคำตอบ ≠ ไม่ได้สร้าง" — ยิงซ้ำคือวิธีที่ทำให้เกิดเอกสารซ้ำในระบบลูกค้า

reference ของ status-codes ต้องมีตารางสถานะหลังสร้าง (รออนุมัติ = ถูกต้องแล้ว ·
อนุมัติแล้ว = skill นี้ต้องไม่ทำให้เกิด ถ้าเจอแปลว่ามีคนอนุมัติจากที่อื่น · ยกเลิกแล้ว = รายงานอย่างเดียว)
พร้อมคำเตือนว่า **เจอรหัสที่ไม่มีในตาราง ห้ามเดาความหมาย** ให้แสดงข้อความดิบให้ผู้ใช้เห็นแล้วหยุด

## ฌ. ไฟล์แนบ — ข้อจำกัดที่ต้องบอกผู้ใช้ทุกครั้ง

MCP ไม่มี tool อัปโหลดไฟล์แนบเข้าเอกสารค่าใช้จ่าย เอกสารที่สร้างจะไม่มีไฟล์แนบ
ทางออกที่ทำได้: ใส่ path ของไฟล์ต้นฉบับลงในหมายเหตุภายใน เพื่อให้ตามรอยกลับได้
แล้วให้ผู้ใช้เปิดเอกสารในระบบแล้วแนบเอง

**ต้องแจ้งผู้ใช้ทุกครั้งว่าไฟล์ยังไม่ได้แนบ** อย่าปล่อยให้เข้าใจผิดว่าแนบแล้ว

## ญ. ภาษีหัก ณ ที่จ่าย

**ดูจากเอกสารว่าหักจริงหรือไม่ อย่าคำนวณเพิ่มเอง**
ยอดที่จ่ายจริง = ยอดรวมทั้งสิ้น → ไม่ได้หัก อย่าใส่ WHT ·
ยอดที่จ่ายจริง < ยอดรวม → หักแล้ว ใส่อัตราตามเอกสาร

ถ้าเอกสารเข้าข่ายต้องหักแต่ไม่ได้หัก → แจ้งเตือนว่าอาจมีประเด็นภาษี
**แต่ยังบันทึกตามความจริงที่เกิดขึ้น** — หน้าที่ของ skill คือบันทึกสิ่งที่เกิด ไม่ใช่สิ่งที่ควรเกิด

## ฎ. ตารางว่างานไหนส่งให้ subagent ตัวไหน และเพราะอะไร

ค้นเอกสารซ้ำ/ค้น vendor/ดึงยอด → subagent ที่ไม่มี tool เขียน (ผลค้นหากิน context และปลอดภัยแม้สั่งผิด) ·
ตรวจตาราง preview → ผู้ตรวจอิสระ · ตรวจความเสี่ยงภาษี → subagent ภาษี

# กฎห้าม — ต้องเขียนเป็นหัวข้อของตัวเอง

1. **ห้ามสร้างเอกสารโดยไม่ผ่านการอนุมัติของผู้ใช้** — ต้อง preview ทั้งกองก่อนเสมอ
2. **ห้ามสร้าง vendor ใหม่ก่อนค้นหาให้ครบทุกวิธี**
3. **ห้ามเดาหมวดหมู่หรือรหัสบัญชีแล้วบันทึกเลย** ต่ำกว่าเกณฑ์ความมั่นใจ → ถามผู้ใช้
4. **ห้ามยิงซ้ำเมื่อ response หลุด** — ตรวจสถานะก่อนเสมอ
5. **ห้ามสร้างเอกสารสถานะอื่นนอกจากรออนุมัติ** และห้ามอนุมัติ/ยกเลิก/ลบ/บันทึกจ่ายชำระ/ส่งอีเมล
6. **ห้ามปิดกลไกกันซ้ำ** ด้วย flag ใด ๆ
7. **ถ้าไม่มีอะไรต้องบันทึก ให้บอกตรง ๆ** อย่าสร้างงานปลอมขึ้นมา
8. **ห้ามบันทึกเมื่อบริษัทปลายทางไม่ตรงกับ client-profile.md**
9. ข้อมูลถูกส่งออกไปยังระบบภายนอกผ่าน MCP — ผู้ใช้รับผิดชอบ PDPA และสิทธิ์เข้าถึงบัญชีลูกค้า

# หัวข้อที่ SKILL.md ต้องมี เรียงตามนี้

1. ชื่อ + ตำแหน่งในสายงาน (ขั้นสุดท้าย) + ต้องใช้คู่กับ plugin หลัก
2. กฎที่ต้องใช้วิจารณญาณ (5 ข้อแรกของกฎห้าม)
3. ขอบเขต — รองรับเฉพาะเอกสารฝั่งซื้อที่ตรวจแล้ว / ไม่รองรับฝั่งขาย การอนุมัติ การจ่ายชำระ
   void ลบเอกสาร การแนบไฟล์ และการแก้ผังบัญชี
4. ขั้นตอน Step 0 ถึง Step 9
5. ตารางการใช้ subagent
6. หัวข้อภาษีหัก ณ ที่จ่าย
7. ข้อจำกัดและสิ่งที่ผู้ใช้ต้องตรวจเอง

หัวข้อ 7 ต้องพูดตรง ๆ ว่า: เอกสารอยู่ในสถานะรออนุมัติ ผู้ใช้ต้องตรวจและอนุมัติเอง ·
**ไฟล์เอกสารต้นฉบับไม่ถูกแนบ** · หมวดหมู่ที่จับคู่ให้เป็นการอนุมาน ต้องตรวจทุกใบ
โดยเฉพาะเส้นแบ่ง ต้นทุน/ค่าใช้จ่าย/ทรัพย์สิน ซึ่งกระทบทั้งงบและภาษี ·
ไม่ตัดสินรายจ่ายต้องห้ามตามมาตรา 65 ตรี และไม่ตัดสินสิทธิขอคืนภาษีซื้อ ·
**การกันซ้ำอาศัยเลขที่เอกสารของผู้ขาย — ถ้าเอกสารไม่มีเลขที่ หรือ OCR อ่านผิด การกันซ้ำจะไม่ทำงาน** ·
ยอดคงเหลือและรายงานภาษีในระบบต้องกระทบยอดเองอีกชั้น
