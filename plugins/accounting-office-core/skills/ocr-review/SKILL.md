# ตรวจผล OCR — คัดเฉพาะรายการที่ต้องแก้มือ

งานนี้ไม่ใช่การอ่านเอกสารใหม่ แต่คือการ **ตรวจผลที่อ่านมาแล้ว** ว่าเชื่อได้แค่ไหน
ผลลัพธ์คือ `exceptions.xlsx` ที่มีเฉพาะแถวที่คนต้องเข้าไปดู — ไม่ใช่รายงานทั้งกอง

---

## กฎบังคับ (ทุก skill ในชุดนี้ใช้เหมือนกัน)

1. **ทำงานเฉพาะในโฟลเดอร์ลูกค้าที่ผู้ใช้ระบุ** ห้ามอ่านหรือเขียนโฟลเดอร์ลูกค้ารายอื่น
2. **อ่าน `client-profile.md` ก่อนเริ่มงานทุกครั้ง** ถ้าไม่มี ให้หยุดแล้วบอกผู้ใช้ให้รัน `/new-client` ก่อน
3. **ก่อน action ที่เขียนข้อมูลเข้า ERP** ต้องแสดงชื่อบริษัทและเลขผู้เสียภาษีของบริษัทปลายทางใน ERP แล้วเทียบกับ `client-profile.md` — ถ้าไม่ตรง **หยุดทันที**
4. **สร้างเอกสารใน ERP เป็นสถานะรออนุมัติเท่านั้น** ห้ามอนุมัติ ห้ามบันทึกรับชำระ ห้าม void ห้ามลบ
5. **ใส่ชื่อ plugin และเลขเวอร์ชันไว้ในหัวทุกไฟล์ที่สร้าง** เช่น `accounting-office-core v1.0.0 — 2569-09-16`

---

## ขอบเขต

**รองรับ**
- ผล OCR ในรูป `.xlsx` / `.csv` / `.json` ที่มี 1 แถว = 1 เอกสาร
- เอกสารฝั่งซื้อ: ใบกำกับภาษีเต็มรูป ใบกำกับภาษีอย่างย่อ ใบเสร็จรับเงิน ใบแจ้งหนี้
- ตรวจย้อนกลับไปที่ภาพต้นฉบับใน `source-docs/` เมื่อ flag ขึ้น

**ไม่รองรับ**
- การ OCR เอง (ถ้ายังไม่มีผล OCR ให้แจ้งผู้ใช้ว่าต้องรันเครื่องมือ OCR ก่อน)
- การตัดสินว่ารายจ่ายนั้น **ต้องห้ามทางภาษี** หรือไม่ — เป็นดุลพินิจผู้ทำบัญชี
- การตรวจว่าผู้ขายอยู่ในระบบ VAT จริงหรือไม่ (ต้องเช็คที่ rd.go.th เอง)

## ขั้นตอนการทำงาน

### Step 1 — โหลดบริบท

1. อ่าน `client-profile.md` → เก็บ ชื่อบริษัท, เลขผู้เสียภาษี, สถานะ VAT, รอบบัญชี
2. อ่าน `mapping-overrides.md` ถ้ามี
3. อ่านไฟล์ผล OCR ใน `<งวด>/ocr-output/`
4. **แสดง column ที่เจอให้ผู้ใช้ยืนยัน mapping ก่อน** — column ไหนคือเลขที่เอกสาร วันที่ ยอดก่อน VAT VAT ยอดรวม เลขผู้เสียภาษีผู้ขาย

### Step 2 — ตรวจทีละกฎ

ตรวจครบทุกกฎกับทุกแถว แล้วเก็บ flag สะสม (1 แถวมีได้หลาย flag)

| รหัส | กฎ | เงื่อนไขที่ถือว่าผิด | ระดับ |
|---|---|---|---|
| `TAXID_LEN` | เลขผู้เสียภาษีผู้ขาย | ไม่ครบ 13 หลักหลังลบช่องว่าง/ขีด | ต้องแก้ |
| `TAXID_SUM` | checksum เลข 13 หลัก | คำนวณตาม `references/tax-id-checksum.md` แล้วไม่ผ่าน | ต้องแก้ |
| `VAT_MATH` | คณิตศาสตร์ VAT | `|ยอดก่อน VAT × 0.07 − VAT| > 0.02` | ต้องแก้ |
| `VAT_SUM` | ยอดรวม | `ยอดก่อน VAT + VAT ≠ ยอดรวม` (เกิน ±0.02) | ต้องแก้ |
| `VAT_RATE` | อัตรา VAT ผิดยุค | VAT/ยอดก่อน VAT ไม่ใช่ 0% หรือ ~7% | ต้องดู |
| `DATE_ERA` | ปี พ.ศ./ค.ศ. | ปีอยู่นอกช่วง 2560–2580 (พ.ศ.) หรือ 2017–2037 (ค.ศ.) | ต้องแก้ |
| `DATE_PERIOD` | วันที่นอกงวด | วันที่เอกสารไม่อยู่ในงวดที่กำลังทำ | ต้องดู |
| `DATE_AMBIG` | วัน/เดือนกำกวม | ทั้งสองค่า ≤ 12 และรูปแบบไม่ชัด | ต้องแก้ |
| `DOC_DUP` | เอกสารซ้ำ | เลขที่เอกสาร + เลขผู้เสียภาษีผู้ขาย ซ้ำในงวดเดียวกัน | ต้องแก้ |
| `DOC_MISSING` | ไม่มีเลขที่เอกสาร | ช่องว่าง | ต้องแก้ |
| `AMT_ZERO` | ยอดเป็น 0 หรือติดลบ | ยอดรวม ≤ 0 | ต้องแก้ |
| `AMT_OUTLIER` | ยอดผิดปกติ | สูงกว่า median ของงวดเกิน 10 เท่า | ต้องดู |
| `VAT_ABBREV` | ใบกำกับภาษีอย่างย่อ | ประเภทเอกสารเป็นอย่างย่อ แต่มีการขอคืน VAT | ต้องดู |
| `NO_VAT_CLAIM` | ลูกค้าไม่จด VAT | `client-profile.md` ระบุไม่จด VAT แต่มีแถวที่แยก VAT | ต้องดู |
| `LOW_CONF` | OCR ไม่มั่นใจ | ถ้าไฟล์มี column confidence และค่า < 0.80 | ต้องดู |

รายละเอียดกฎ VAT อยู่ใน `references/vat-rules.md`

### Step 3 — เปิดภาพต้นฉบับเฉพาะแถวที่ flag

สำหรับแถวระดับ **ต้องแก้** ให้เปิดไฟล์ภาพที่อ้างถึงใน `source-docs/` แล้วอ่านซ้ำด้วยตาตัวเอง
แล้วเติมค่าที่อ่านได้ลงในช่อง `ค่าที่ควรเป็น`

**ห้ามเดา** — ถ้าภาพไม่ชัด ให้เขียนว่า `อ่านไม่ออก` แล้วปล่อยให้คนตัดสิน
การเดาตัวเลขให้ดูเรียบร้อย อันตรายกว่าการบอกว่าอ่านไม่ออก

### Step 4 — ออก exceptions.xlsx

บันทึกที่ `<งวด>/output/exceptions.xlsx`

**Sheet `EXCEPTIONS`** — เฉพาะแถวที่มี flag เท่านั้น

| Column | คำอธิบาย |
|---|---|
| `แถวที่` | เลขแถวในไฟล์ OCR ต้นทาง |
| `ไฟล์ต้นฉบับ` | ชื่อไฟล์ใน `source-docs/` |
| `ผู้ขาย` | ตามที่ OCR อ่านได้ |
| `เลขที่เอกสาร` | |
| `วันที่` | |
| `ยอดรวม` | |
| `รหัส flag` | เช่น `VAT_MATH; TAXID_SUM` |
| `ระดับ` | ต้องแก้ / ต้องดู |
| `ค่าที่ OCR อ่านได้` | |
| `ค่าที่ควรเป็น` | เติมจาก Step 3 หรือ `อ่านไม่ออก` |
| `ผู้ตรวจแก้` | เว้นว่างให้คนกรอก |
| `แก้แล้ว` | เว้นว่างให้คนกรอก |

**สี:** แดงอ่อน `#FFC7CE` = ต้องแก้ · เหลืองอ่อน `#FFEB9C` = ต้องดู

**Sheet `SUMMARY`**
- หัวไฟล์: `accounting-office-core v1.0.0 | ลูกค้า: <ชื่อ> | งวด: <งวด> | สร้างเมื่อ: <วันที่>`
- จำนวนเอกสารทั้งหมด / ผ่านทั้งหมด / ต้องแก้ / ต้องดู
- นับจำนวนแต่ละรหัส flag เรียงมากไปน้อย
- ยอดเงินรวมของแถวที่ติด flag

**Sheet `CLEAN`** — แถวที่ผ่านทุกกฎ พร้อมนำไปใช้ต่อใน `/vouch-expense` หรือ post เข้า ERP

แล้วชี้ว่าควรแก้อะไรก่อน — เรียงตามยอดเงินที่เกี่ยวข้อง ไม่ใช่ตามจำนวนใบ

## Edge cases ที่เจอจริง

| สถานการณ์ | วิธีจัดการ |
|---|---|
| ใบกำกับภาษีมีหลายหน้า OCR แยกเป็นหลายแถว | รวมแถวที่เลขที่เอกสารเดียวกัน ใช้ยอดจากหน้าสรุป ไม่ใช่บวกทุกหน้า |
| สินค้า Non-VAT ปนในใบเดียวกัน | `ยอดก่อน VAT × 1.07 ≠ ยอดรวม` เป็นเรื่องปกติ — ต้องดูช่อง "มูลค่าที่ยกเว้นภาษี" ก่อน flag `VAT_SUM` |
| ส่วนลดท้ายเอกสาร | คำนวณ VAT จากยอดหลังหักส่วนลด ไม่ใช่ก่อนหัก |
| เลขผู้เสียภาษีบุคคลธรรมดา | ใช้ checksum เดียวกับนิติบุคคล — 13 หลักเหมือนกัน |
| ผู้ขายเป็นบุคคลธรรมดาไม่จด VAT | ไม่มี VAT เป็นเรื่องถูกต้อง อย่า flag `VAT_MATH` |
| เอกสารข้ามงวด (ใบเดือน ส.ค. เพิ่งได้เดือน ก.ย.) | flag `DATE_PERIOD` แต่ไม่ใช่ความผิด — VAT ซื้อขอคืนย้อนหลังได้ 6 เดือน ดู `references/vat-rules.md` |
| ไฟล์ OCR ไม่มี column confidence | ข้ามกฎ `LOW_CONF` แล้วระบุใน SUMMARY ว่าข้ามเพราะไม่มีข้อมูล |

## ข้อจำกัดและสิ่งที่ผู้ใช้ต้องตรวจเอง

- **แถวที่อยู่ใน `CLEAN` คือ "ผ่านกฎที่ตั้งไว้" ไม่ใช่ "ถูกต้องแน่นอน"** — OCR อ่านยอดผิดเป็นตัวเลขที่ยังคำนวณลงตัวได้
- ไม่ตรวจว่าผู้ขายมีตัวตนจริง ไม่ตรวจว่าจดทะเบียน VAT จริง และ **ไม่ตรวจใบกำกับภาษีปลอม**
- checksum ที่ผ่าน แปลว่าเลขมีโครงสร้างถูก ไม่ได้แปลว่าเป็นเลขของผู้ขายรายนั้นจริง
- ไม่ตัดสินว่ารายจ่ายเป็นรายจ่ายต้องห้ามตามมาตรา 65 ตรี — เป็นดุลพินิจผู้ทำบัญชี
- ไม่ตรวจว่าใบกำกับภาษีมีรายการครบตามมาตรา 86/4 หรือไม่ทุกข้อ — ตรวจเฉพาะที่ OCR ดึงมาได้
- เอกสารมีเลขประจำตัวผู้เสียภาษีซึ่งเป็นข้อมูลส่วนบุคคลตาม PDPA — ทำงานบนเครื่องสำนักงานเท่านั้น
