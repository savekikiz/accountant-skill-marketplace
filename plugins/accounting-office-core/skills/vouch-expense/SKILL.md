# Vouch ค่าใช้จ่าย — รายการที่บันทึก ↔ เอกสารต้นฉบับ

ตอบคำถามเดียว: **รายการที่ลงบัญชีไว้ มีเอกสารรองรับจริงหรือไม่ และตรงกันไหม**
ทิศทางคือ จากสมุดบัญชี → ไปหาเอกสาร (vouching) ไม่ใช่ทางกลับ

---

## กฎบังคับ

กฎ 🔒 บังคับด้วย hook ของ plugin — ทำผิดแล้ว tool call จะถูกปฏิเสธ ไม่ใช่แค่คำเตือน

| กฎ | บังคับโดย |
|---|---|
| ทำงานได้ทีละลูกค้า — โฟลเดอร์รายอื่นถูกบล็อกทั้ง session | 🔒 hook |
| ต้องอ่าน `client-profile.md` ก่อน จึงจะแตะโฟลเดอร์ลูกค้าได้ | 🔒 hook |
| เขียนได้เฉพาะ `<งวด>/output/` — `ocr-output/` `source-docs/` `bank/` อ่านอย่างเดียว | 🔒 hook |
| ห้ามเขียนทับ `client-profile.md` / `mapping-overrides.md` ที่มีอยู่ และห้ามสร้าง `chart-of-accounts.xlsx` | 🔒 hook |
| หัวไฟล์ระบุ plugin + เวอร์ชัน | 🔒 hook (เติมให้เองตอนเขียนลง `output/`) |

> `<เวอร์ชัน>` ในตัวอย่างข้างล่างคือเลขจริงจาก `plugin.json` — hook เติมให้ตอนเขียนไฟล์
> ไม่ต้องพิมพ์เอง และอย่า hardcode เลขเวอร์ชันลงในไฟล์ผลลัพธ์
| ขณะทำงานลูกค้า ห้ามต่อเน็ต/ใช้ MCP ที่ไม่ใช่ ERP/ส่งอีเมล (PDPA) | 🔒 hook |

ที่เหลือเป็นเรื่องที่ต้องใช้วิจารณญาณ — hook ตรวจแทนไม่ได้:

- **ห้ามเดา** ถ้าอ่านไม่ออกหรือไม่แน่ใจ ให้บันทึกว่าไม่แน่ใจแล้วถามผู้ใช้ อย่าเติมค่าให้ดูสมบูรณ์
- **ถ้าไม่ระบุโฟลเดอร์ลูกค้า/งวด ให้ถามก่อน** อย่าเดา อย่าไล่สแกนทั้งเครื่อง

## ขอบเขต

**รองรับ**
- รายการค่าใช้จ่ายในรูป `.xlsx` / `.csv` — ทั้ง format Express X Import (header 4 แถว) และ format ทั่วไป (header 1 แถว)
- เอกสารต้นฉบับ: `.jpg`, `.png`, `.heic`, `.pdf` ในโฟลเดอร์ `<งวด>/source-docs/`
- ใช้ผล `CLEAN` จาก `/review-ocr` เป็น input ได้โดยตรง (เร็วกว่าและแม่นกว่า)

**ไม่รองรับ**
- Vouch ฝั่งรายได้ (ทิศทางกลับกัน — ต้องใช้ tracing ไม่ใช่ vouching)
- การตัดสินว่ารายจ่ายหักภาษีได้หรือไม่ได้ตามมาตรา 65 ตรี
- การแก้ไขรายการในไฟล์ต้นทางให้ — skill นี้ **อ่านอย่างเดียว** แล้วออกไฟล์ผลใหม่

## ขั้นตอนการทำงาน

### Step 1 — โหลดบริบทและยืนยัน mapping

1. อ่าน `client-profile.md` และ `mapping-overrides.md`
2. อ่านไฟล์รายการค่าใช้จ่าย ตรวจว่าเป็น Express format หรือ format ทั่วไป
3. **แสดงสรุปให้ผู้ใช้ยืนยันก่อนเริ่ม** — จำนวนรายการ, ช่วงวันที่, ยอดรวม, ตัวอย่าง 3 แถวแรก
4. ยืนยัน column mapping: เลขที่เอกสาร / วันที่ / ยอดก่อน VAT / VAT / ยอดรวม / ชื่อผู้ขาย
5. ถามว่าเอกสารต้นฉบับอยู่ที่ไหน ถ้าไม่ใช่ `<งวด>/source-docs/`

> ถ้าช่วงวันที่ในไฟล์ไม่ตรงกับงวดที่ผู้ใช้บอก ให้ทักก่อน อย่าเดินหน้าเงียบๆ

### Step 2 — อ่านเอกสารต้นฉบับ

อ่านทุกไฟล์ในโฟลเดอร์เอกสาร ดึงข้อมูลต่อไปนี้ต่อ 1 ใบ:

```
doc_number      เลขที่เอกสาร (เลขที่ใบเสร็จ / ใบกำกับภาษี)
doc_date        วันที่ออกเอกสาร (บันทึกไว้ว่าเป็น พ.ศ. หรือ ค.ศ.)
supplier        ชื่อผู้ขาย
supplier_taxid  เลขผู้เสียภาษีผู้ขาย 13 หลัก (ถ้ามี)
total_excl_vat  ยอดก่อน VAT
vat_amount      VAT
total_incl_vat  ยอดรวมทั้งสิ้น
doc_type        ใบกำกับภาษีเต็มรูป / อย่างย่อ / ใบเสร็จ / ใบแจ้งหนี้
source_file     ชื่อไฟล์
```

สร้าง index: `normalize(doc_number) → [รายการเอกสาร]` (เป็น list เพราะอาจซ้ำ)

**ถ้าเอกสาร 1 ใบถูกสแกนเป็นหลายไฟล์/หลายหน้า** (เช่น ใบเสร็จ Makro ที่รายการยาว)
ให้รวมเป็นใบเดียวโดยใช้ **ยอดจากหน้าสรุป** ไม่ใช่บวกยอดทุกหน้า

**ห้ามเดา** ถ้าอ่านไม่ออก ให้บันทึกเป็น `อ่านไม่ออก` แล้วให้ผลออกมาเป็นสถานะ "ต้องตรวจมือ"

### Step 3 — Match

```python
def normalize_docnum(s):
    return str(s).strip().upper().replace(" ", "").replace("-", "").replace("/", "")
```

#### ระดับ 1 — จับคู่ด้วยเลขที่เอกสาร
พบคู่ → ไประดับ 2 · ไม่พบ → ลองระดับ 1.5

#### ระดับ 1.5 — จับคู่สำรอง (เมื่อเลขที่เอกสารอ่านไม่ได้/ไม่ตรง)
ต้องเข้าเงื่อนไข **ทั้ง 3 ข้อ**: ยอดรวมตรง ±1 บาท · วันที่ห่างไม่เกิน ±3 วัน · ชื่อผู้ขายคล้ายกัน
ถ้าเข้าเงื่อนไข → สถานะ `พบ (จับคู่จากยอด+วันที่)` และ **ต้องให้คนยืนยัน** ทุกใบ

#### ระดับ 2 — เทียบยอด
```
ยอดในรายการ = ยอดก่อน VAT + VAT   (หรือ column ยอดรวมถ้ามี)
ผลต่าง       = |ยอดในรายการ − ยอดรวมในเอกสาร|

ผลต่าง ≤ 1.00 บาท           → ตรง
ผลต่าง ≤ 5% ของยอด          → ยอดต่าง (ดูสาเหตุ: สินค้า Non-VAT, ส่วนลด, WHT)
ผลต่างมากกว่านั้น            → ยอดต่างมาก ต้องสอบสวน
```

> ก่อนสรุปว่า "ยอดต่าง" ให้ลองตรวจว่าผลต่างเท่ากับ **ภาษีหัก ณ ที่จ่าย** ที่อัตรามาตรฐาน
> (1%, 2%, 3%, 5%) ของยอดก่อน VAT หรือไม่ ถ้าใช่ ให้ระบุไว้ในเหตุผล

#### ระดับ 3 — ตรวจเพิ่ม
- **วันที่** ห่างเกิน ±3 วัน → หมายเหตุ `cut-off` (ไม่ลดระดับสถานะ แต่ต้องบันทึกไว้)
- **เลขที่ซ้ำในรายการ** → `รายการซ้ำ` — เสี่ยงบันทึกซ้ำ
- **เลขที่ซ้ำในโฟลเดอร์เอกสาร** → `มีเอกสาร N ชุด` — เสี่ยงใช้เอกสารเดียวลง 2 ครั้ง
- **ชื่อผู้ขายไม่ใกล้เคียง** ทั้งที่เลขที่เอกสารตรง → หมายเหตุให้คนดู

### Step 4 — ออกไฟล์ผล

บันทึกที่ `<งวด>/output/vouch-<ชื่อไฟล์ต้นทาง>.xlsx`

**Sheet `VOUCH`** = ทุก column เดิมของไฟล์ต้นทาง + 4 column ใหม่ต่อท้าย

| Column | ค่า |
|---|---|
| `vouch_status` | `พบ ✅` / `พบ — ยอดต่าง ⚠️` / `พบ — เอกสารซ้ำ ⚠️` / `พบ (จับคู่จากยอด+วันที่) ⚠️` / `ไม่พบเอกสาร ❌` / `ต้องตรวจมือ ⚠️` |
| `vouch_reason` | พบในไฟล์ไหน, วันที่/ผู้ขายในเอกสาร, ยอดที่เทียบ, ผลต่างและสาเหตุที่สันนิษฐาน |
| `vouch_file` | ชื่อไฟล์เอกสารที่จับคู่ได้ (ว่างถ้าไม่พบ) |
| `vouch_diff` | ผลต่างเป็นตัวเลข (บวก = รายการสูงกว่าเอกสาร) |

**สี:** เขียว `#C6EFCE` พบ · เหลือง `#FFEB9C` ยอดต่าง/ต้องตรวจมือ · ส้ม `#F4B942` เอกสารซ้ำ · แดง `#FFC7CE` ไม่พบ

**Sheet `SUMMARY`**
- หัวไฟล์: `accounting-office-core v<เวอร์ชัน> | ลูกค้า: <ชื่อ> | งวด: <งวด> | สร้างเมื่อ: <วันที่>`
- จำนวนและ % ของแต่ละสถานะ
- ยอดรวมที่ตรวจ / ยอดรวมของรายการที่ยังมีปัญหา
- **รายการเอกสารในโฟลเดอร์ที่ไม่ถูกจับคู่กับรายการใดเลย** — อาจแปลว่ายังลงบัญชีไม่ครบ

### Step 4.5 — ตรวจความเสี่ยงภาษี (ถ้าผู้ใช้ต้องการ)

หลังได้ไฟล์ผลแล้ว ถามผู้ใช้ว่าต้องการให้ตรวจความเสี่ยงภาษีของกองนี้ด้วยหรือไม่
ถ้าต้องการ ให้ส่ง path ของไฟล์ผลและโฟลเดอร์ลูกค้าให้ `tax-compliance-checker`

ตัวนั้นจะไล่หา: รายการที่ควรหัก ณ ที่จ่ายแต่ไม่ได้หัก · ใบกำกับภาษีอย่างย่อที่ขอคืน VAT ไม่ได้ ·
รายจ่ายที่อาจเป็นรายจ่ายต้องห้าม · ทรัพย์สินที่ถูกลงเป็นค่าใช้จ่ายงวดเดียว

**นำผลมารายงานตามที่ผู้ตรวจเขียน อย่าลดระดับความรุนแรงเอง** และคงการแบ่ง
`ผิดแน่ / น่าสงสัย / ต้องถามเพิ่ม` ไว้ตามเดิม

  พบ ✅              : N  (X%)

| ผลที่เจอ | assertion ที่กระทบ |

| ไม่พบเอกสาร | Existence / Occurrence |

## Edge cases ที่เจอจริง

| สถานการณ์ | วิธีจัดการ |
|---|---|
| ใบเสร็จร้านค้าปลีก ยอดในรายการ ≠ ยอดในใบเสร็จ | มีสินค้า Non-VAT ปน — ใช้ `ยอดก่อน VAT + VAT` เทียบ ไม่ใช่ `ยอดก่อน VAT × 1.07` |
| เลขที่เอกสารรูปแบบต่างกัน (`ES-6807001` vs `ES6807001`) | normalize ก่อน match |
| ใบกำกับภาษีมาทีหลัง มีแต่ใบส่งของ | สถานะ `พบ` แต่ระบุใน reason ว่าเอกสารที่พบไม่ใช่ใบกำกับภาษี |
| จ่ายเป็นงวด ใบแจ้งหนี้ใบเดียวแต่ลงหลายรายการ | 1 เอกสาร ↔ หลายรายการ ถือว่าถูก แต่ผลรวมต้องเท่ายอดในเอกสาร ไม่งั้น flag |
| วันที่ในเอกสารเป็น พ.ศ. แต่ในไฟล์เป็น ค.ศ. | normalize เป็นรูปแบบเดียวกันก่อนเทียบ อย่าปล่อยให้ต่างกัน 543 ปี |
| ภาพเบลอ/ถ่ายเอียง | `ต้องตรวจมือ ⚠️` พร้อมระบุว่าอ่านส่วนไหนไม่ออก |
| เอกสารเป็นภาษาอังกฤษล้วน | ใช้ได้ปกติ — จับคู่ด้วยเลขที่เอกสารและยอดเป็นหลัก |

## ข้อจำกัดและสิ่งที่ผู้ใช้ต้องตรวจเอง

- **`พบ ✅` แปลว่า "จับคู่ได้ตามเงื่อนไขที่ตั้งไว้" ไม่ใช่ "รายการถูกต้อง"** — ทุกบรรทัดยังต้องผ่านสายตาผู้ทำบัญชี
- การจับคู่ระดับ 1.5 (ยอด+วันที่) **เสี่ยง false positive สูง** — ต้องเปิดดูทุกใบก่อนเชื่อ
- ไม่ตรวจว่าเอกสารเป็นของแท้ ไม่ตรวจลายเซ็นอนุมัติ และ **ไม่ตรวจจับการทุจริต**
- ไม่ตรวจว่ารายจ่ายนั้นเกี่ยวกับกิจการจริงหรือไม่ (assertion Occurrence เชิงเนื้อหา)
- ไม่ตัดสินว่าเป็นรายจ่ายต้องห้ามตามมาตรา 65 ตรี และไม่ตัดสินสิทธิขอคืนภาษีซื้อ
- ไม่แก้ไขไฟล์ต้นทาง — ถ้าต้องแก้ ผู้ใช้แก้เองแล้วรันซ้ำ
- เอกสารมีข้อมูลส่วนบุคคลตาม PDPA — ทำงานบนเครื่องสำนักงานเท่านั้น
