# จับคู่หมวดหมู่ค่าใช้จ่าย FlowAccount

> ⚠️ **`category_id` เป็นค่าเฉพาะของแต่ละบริษัท ไม่ใช่ค่ากลาง**
> ต้องดึงสดด้วย `expense__list_business_categories` ของบริษัทนั้นทุกครั้ง
> **ห้ามใช้ `category_id` จากลูกค้ารายอื่นข้ามกัน** — จะลงบัญชีผิดผัง

---

## ลำดับความสำคัญในการตัดสิน

1. **`mapping-overrides.md` ของลูกค้ารายนั้น** — ชนะทุกกฎด้านล่าง
2. **ผังบัญชีของลูกค้า** (`chart-of-accounts.xlsx`) ถ้ามี
3. กฎทั่วไปด้านล่าง
4. **ถ้ายังไม่ชัด → ถามผู้ใช้** ห้ามเดา

---

## กฎทั่วไป

### กฎที่ 1 — ดูสิ่งที่ซื้อ ไม่ใช่ชื่อผู้ขาย
ซื้อกระดาษจากร้านคอมพิวเตอร์ = วัสดุสำนักงาน ไม่ใช่อุปกรณ์ไอที

### กฎที่ 2 — แยกทรัพย์สินออกจากค่าใช้จ่าย
ของที่ใช้ได้เกิน 1 ปี และมีมูลค่าสูง → บันทึกเป็น **ทรัพย์สิน** (ตัดค่าเสื่อม)
ไม่ใช่ค่าใช้จ่ายงวดเดียว

**เกณฑ์มูลค่าขั้นต่ำเป็นนโยบายของแต่ละกิจการ** — ถ้า `client-profile.md`
หรือ `mapping-overrides.md` ไม่ได้ระบุไว้ ให้ **ถามผู้ใช้** อย่าตั้งเกณฑ์เอง
ข้อนี้กระทบทั้งงบการเงินและภาษีเงินได้นิติบุคคล จึงห้ามเดาเด็ดขาด

### กฎที่ 3 — ต้นทุน vs ค่าใช้จ่าย
- ซื้อมาเพื่อส่งมอบให้ลูกค้าโดยตรง → **ต้นทุน** (5xxxx ต้นทุนขาย/ต้นทุนบริการ)
- ใช้ภายในกิจการ → **ค่าใช้จ่าย** (5xxxx ค่าใช้จ่ายในการขาย/บริหาร)

### กฎที่ 4 — ซื้อของ vs จ้างคน
- ซื้อ **ของ/วัสดุ** ที่ใช้ในการส่งมอบบริการ → ต้นทุนบริการ
- จ้าง **คน/บริษัทอื่น** ทำงานให้ → ค่าบริการ/ค่าจ้างทำของ
- ก้ำกึ่ง (เช่น เช่าระบบเสียงพร้อมทีมงานมาจัดงานให้ลูกค้า) → **ถามผู้ใช้**

### กฎที่ 5 — SaaS vs License ถาวร
- จ่ายรายเดือน/รายปี (Google Workspace, Claude, Canva, cloud server) → **ค่าใช้จ่าย** หมวดซอฟต์แวร์
- ซื้อ license ถาวร หรือจ้างพัฒนาระบบ → **ทรัพย์สินไม่มีตัวตน** (ตัดจำหน่าย)

### กฎที่ 6 — หมวด "ค่าใช้จ่ายเบ็ดเตล็ด" คือทางออกสุดท้าย
ถ้าจะใช้ **ต้องถามผู้ใช้ก่อนเสมอ** หมวดนี้ทำให้ตรวจสอบย้อนหลังยาก

### กฎที่ 7 — หมวด "ส่วนตัว" / "รายจ่ายต้องห้าม"
ใช้เฉพาะเมื่อผู้ใช้ **ยืนยันชัดเจน** เท่านั้น เพราะกระทบการคำนวณภาษีเงินได้นิติบุคคลโดยตรง

## กลุ่มหมวดหมู่ที่ FlowAccount มักมีให้ (ใช้ระบุกลุ่ม แล้วไปหา id จริง)

| กลุ่ม | ตัวอย่างรายการที่เข้ากลุ่มนี้ |
|---|---|
| ขายและการตลาด | ค่าโฆษณา, ส่งเสริมการขาย, ค่ารับรองลูกค้า, ค่านายหน้า |
| เดินทาง / ขนส่ง | ค่าเดินทางและที่พัก, ค่าน้ำมัน, ค่าขนส่งสินค้า |
| สำนักงาน | ค่าเช่าออฟฟิศ, วัสดุสำนักงาน, ค่าไฟ, ค่าน้ำ, โทรศัพท์, อินเทอร์เน็ต, ค่าส่งเอกสาร, ซอฟต์แวร์ |
| ค่าจ้าง / บริการ | บริการทั่วไป/ฟรีแลนซ์, ค่าทำบัญชี, ค่าที่ปรึกษา, ค่าสอบบัญชี |
| สินค้า / วัตถุดิบ | ซื้อสินค้าไว้ขาย, ซื้อของ/วัสดุไว้ให้บริการ, สินค้าตัวอย่าง |
| ทรัพย์สิน | คอมพิวเตอร์/อุปกรณ์ไอที, เฟอร์นิเจอร์, ยานพาหนะ, ซอฟต์แวร์ (license ถาวร) |
| เงินเดือน / สวัสดิการ | เงินเดือน, ค่าล่วงเวลา, เบี้ยเลี้ยง, ประกันสังคม, สวัสดิการพนักงาน |
| อื่นๆ | ค่าเช่า, เบี้ยประกัน, ค่าธรรมเนียมธนาคาร, ภาษีและทะเบียน, ซ่อมแซมบำรุงรักษา, ดอกเบี้ยเงินกู้ |

**วิธีใช้:** ตัดสินว่ารายการอยู่กลุ่มไหนก่อน แล้วค่อยหา `category_id` ที่ตรงที่สุด
จากรายการที่ดึงสดมาของบริษัทนั้น ถ้าในกลุ่มมีหลายตัวใกล้เคียงกัน → เสนอ 2 ตัวเลือกให้ผู้ใช้เลือก

## คู่ที่สับสนบ่อยที่สุด — ต้องระวังเป็นพิเศษ

| คู่ที่สับสน | เส้นแบ่ง |
|---|---|
| ซื้อวัสดุให้บริการ ↔ จ้างบริการภายนอก | ได้ **ของ** มา vs ได้ **แรงงาน/ผลงาน** มา |
| ซอฟต์แวร์ (ค่าใช้จ่าย) ↔ ซอฟต์แวร์ (ทรัพย์สิน) | จ่ายเป็นงวดตามอายุการใช้ vs ได้สิทธิถาวร |
| ค่าเช่า ↔ ค่าบริการ | ผู้เช่าควบคุมการใช้เอง vs มีคนให้บริการมาด้วย (กระทบอัตรา WHT 5% vs 3%) |
| ค่ารับรอง ↔ สวัสดิการพนักงาน | เลี้ยงลูกค้า vs เลี้ยงพนักงาน (ค่ารับรองขอคืน VAT ไม่ได้) |
| อุปกรณ์ไอที (ทรัพย์สิน) ↔ วัสดุสำนักงาน | มูลค่าและอายุการใช้งานตามนโยบายกิจการ |

3 คู่แรกกระทบ **อัตราภาษีหัก ณ ที่จ่าย** และ **สิทธิขอคืนภาษีซื้อ** ด้วย ไม่ใช่แค่ผังบัญชี

## ฟิลด์ที่ต้องส่งตอนสร้างเอกสารค่าใช้จ่าย

```jsonc
{
  "document": {
    "contact_id": "<id ของ vendor ที่ค้นเจอ>",   // ห้ามส่งคู่กับชื่อ vendor
    // "contact_name": "<ชื่อเต็ม>",              // เฉพาะกรณี vendor ใหม่เท่านั้น

    "document_date": "2026-09-05",   // ISO เสมอ แปลง พ.ศ. → ค.ศ. แล้ว
    "due_date": "2026-09-05",        // เงินสด = วันเดียวกับเอกสาร
    "credit_type": "cash",           // cash | credit_days | credit_no_due
    "reference": "INV-001",          // ⭐ เลขที่เอกสารของผู้ขาย — คีย์กันซ้ำ
    "internal_notes": "เอกสารต้นฉบับ: ลูกค้า/<ชื่อ>/<งวด>/source-docs/INV-001.pdf",

    "is_vat_inclusive": false,       // ⚠️ ต้องถามผู้ใช้ ไม่มีค่า default
    "use_inline_vat": true,          // ⚠️ ต้องถามผู้ใช้
    "use_inline_discount": true,     // ⚠️ ต้องถามผู้ใช้

    "items": [
      {
        "name": "<รายการตามเอกสาร>",
        "description": "<รายละเอียด>",
        "quantity": 1,
        "unit_price": 10000.00,      // ราคาก่อน VAT เมื่อ is_vat_inclusive = false
        "is_vat": true,
        "category_id": "<id ที่ดึงสดมา>"   // ⭐ บังคับ
      }
    ]
  },
  "confirm": false                    // รอบแรกเสมอ
}
```

**ตรวจชื่อพารามิเตอร์จริงกับ tool schema ที่โหลดอยู่ในเซสชันเสมอ** โครงข้างบนเป็นรูปแบบที่พบในเวอร์ชันที่ทดสอบไว้

## กับดักที่เจอจริง

### 1. วันที่ พ.ศ. 2 หลัก
`8/7/68` = 8 กรกฎาคม พ.ศ. 2568 → `2568 − 543 = 2025` → `"2025-07-08"`
อย่าอ่านเป็น ค.ศ. 1968 และอย่าสลับเป็น MM/DD แบบอเมริกัน
ถ้าทั้งวันและเดือน ≤ 12 จนกำกวม → **ถามผู้ใช้**

### 2. เลขผู้เสียภาษีจาก OCR มีช่องว่างแทรก
`"01055 67069 510"` → ลบช่องว่าง → `0105567069510` ต้องได้ 13 หลักพอดี
ไม่ครบ → อย่าเดา ให้เปิดภาพดูเอง
ตรวจ checksum ตาม `accounting-office-core` → `skills/ocr-review/references/tax-id-checksum.md`

### 3. ที่อยู่ในเอกสาร ≠ ที่อยู่ในระบบ ได้
ใบเสร็จอาจพิมพ์ที่อยู่สาขา ส่วน contact ในระบบเป็นสำนักงานใหญ่
→ **ใช้ contact เดิม** อย่าสร้างใหม่ แล้วแจ้งผู้ใช้ให้ตรวจ

### 4. `is_vat_inclusive` เดาผิดบ่อยที่สุด
ใบกำกับภาษีไทยที่แยกบรรทัด `รวมเงิน` + `ภาษีมูลค่าเพิ่ม 7%` + `จำนวนเงินทั้งสิ้น`
= ราคา **ยังไม่รวม VAT** → `is_vat_inclusive: false`
ยืนยันด้วยคณิตศาสตร์: `รวมเงิน × 1.07 = จำนวนเงินทั้งสิ้น`

### 5. `category_id` เป็นฟิลด์บังคับ
ถ้าไม่ใส่ preview จะขึ้น warning ว่าบรรทัดยังไม่ถูก map — **ห้ามบันทึกทั้งที่ยัง warning**

### 6. ห้ามพึ่ง idempotency key ที่เราส่งเอง
ค่าที่เราส่งเป็นแค่ correlation id สำหรับ log — คีย์กันซ้ำจริงระบบสร้างเองจากเนื้อหาเอกสาร
ตอนตรวจสถานะต้องใช้ค่า **ที่ response คืนกลับมา**

### 7. ค้นชื่อ vendor ให้ใช้คำสั้น
การค้นเป็น partial match — `"เอิร์ธ"` ได้ผลดีกว่า `"บริษัท เอิร์ธซาวนด์ จำกัด"`
(เว้นวรรคหรือคำนำหน้าต่างกันนิดเดียวก็พลาด)

### 8. เอกสารที่สร้างจะขึ้นสถานะรออนุมัติ
ไม่ใช่ error — เป็นพฤติกรรมที่ต้องการ ผู้ใช้ต้องไปอนุมัติเอง
